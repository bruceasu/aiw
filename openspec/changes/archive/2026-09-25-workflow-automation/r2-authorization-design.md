## 现有接缝与差距

- `workflow.VerificationPlan` schema 1 固定 check_id、argv、目录、超时、网络和环境；selection 只引用计划摘要及 check_id。保留该契约，新增发现范围计划不得悄悄扩张旧计划。
- `FocusedTestAuthorization` / `ConsumeFocusedTestAuthorization` 是精确摘要绑定的一次授权；已 consumed 的记录不迁移成可重复使用的批准。
- `commands/task.ResolveFocusedTestRun`、`ExecuteFocusedTest` 已承接受控执行；真实目录解析和网络执行约束可复用。新核验下沉到受管服务，CLI 仍只负责解析/展示，不能出现绕过 Supervisor 的授权分支。
- `commands/task.localMergeDelivery` 目前允许 waived、使用 add --all，随后调用 `resumeMergedDeliveryCleanup`。这些旧行为不满足新接受与路径范围契约，新链启用前必须替换其资格判断和分步计划执行；不得在外层加一个 grant 后直接沿用全部副作用。
- cleanup 已有 worktree 移除、解除当前绑定、分支删除的恢复顺序，但缺少精确 grant、来源封存与每步目标重检。复用 AIW 内部入口，不能把删除委托给 Agent。

## 1. 授权文件格式与确定性解释

`.ai/<task-id>/grant.md` 是授权依据；采用 UTF-8 Markdown，恰有一个以 `<!-- aiw-grants:v1 -->` / `<!-- /aiw-grants:v1 -->` 包围的 JSON fenced block。外部说明文字不产生权限。JSON 根对象固定为 schema_version=1、task_id、revision、entries；revision 等于条目数量，初始为空。拒绝重复区块、重复 JSON 键、未知字段、尾随 JSON 值、未知版本、错误类型及跨 Task 记录，保留原文件，不从可解析片段推断批准。

entries 按连续 sequence 从 1 递增，条目 ID 在 Task 内唯一；历史条目不可改写。每条字段固定为：

| 字段 | 契约 |
| --- | --- |
| id / sequence / date | 稳定条目 ID、连续序号、RFC3339 时间；时间不用于决定覆盖顺序 |
| permission / approved / reason | 明确能力（test-run、local-delivery、managed-cleanup）、布尔决定、非空理由 |
| authorizer_type / authorizer_id / applicant_stage | user 或 ai 与实际身份分开，记录申请环节；AI 决策绑定其请求/输出证据，不能仅填写 ai 即视为批准 |
| decision_reference | 决策证据的 Task 工件路径与 SHA-256；人工批准保留真实来源，未知人员身份不得伪装为系统用户 |
| plan_reference / policy_reference | 不可变计划和政策工件的路径、schema/version、SHA-256；禁止引用 latest |
| scope / supersedes | scope 固定工作区绑定摘要、允许路径、动作及真实目标；supersedes 为明确被替代的旧条目 ID 数组，无替代时为空 |
| previous_digest / digest | 前一条摘要（首条为空）及当前条摘要；链检查与 Core 已提交尾部锚点共同检测截断/替换 |

摘要使用版本化规范 JSON：对象键按字典序，数组保留约定顺序，UTF-8、无额外空白、无浮点字段；digest 排除自身，包含 previous_digest。集合字段在生成时排序并去重；解析器拒绝非规范集合。规范化只作用于结构，不能改变 argv 顺序、文件内容或真实目标。哈希用于版本/完整性核对，不是签名或越过宿主权限的凭证。

写入由受管授权服务在 R1 Task 锁内比较 revision/尾部摘要，追加条目并持久替换整个文件，再将精确条目及新尾部摘要提交 Core。只读索引可重建，不能成为授权权威。文件先保存而 Core 未提交时，通过相同决策请求及摘要补做登记，不重调模型、不生成另一批准。文件损坏、链与 Core 不符或保存结果未知时停止相关派发，先对账。

执行请求必须引用精确 grant ID/摘要；核验完整日志，后续拒绝或撤销同一计划/能力的决定使旧批准失效。新批准只有显式 supersedes 当前冲突/拒绝条目且范围、政策仍匹配时才能重新授权；拒绝/批准冲突或替代关系不完整时停止，不靠日期或文件最后一条猜测。计划或政策实质变化使用新版本与新决策，不能复活被替代记录。

## 2. 计划、执行清单与核验结果

新范围计划 schema 2 与旧固定 schema 1 使用独立解析分支。范围计划固定 Task、能力、工作区绑定、模块/路径边界、发现规则、受控命令模板、argv 参数约束、允许环境、网络/副作用和资源上限；禁止任意 shell 字符串或从 Agent 输出补入命令。授权绑定计划及政策摘要，不绑定每次新发现的测试文件列表。

每次执行先按固定规则发现测试/fixture，生成不可变执行清单：stage_request_id、Task/Work Item/Attempt、计划/grant/政策引用、具体 argv、cwd、可执行文件及工具链身份、真实路径、输入摘要、超时和宿主约束。范围内新增文件只改变清单/证据；超出范围、命令/网络/副作用或资源放宽使旧授权不适用。工具链/间接脚本环境身份无法完整取得时不得复用旧通过，无法约束实际操作时不得执行。

受管服务逻辑上提供三步（是内部职责契约，不要求新增公共 API）：

1. 保存决策：严格解析及校验决策证据，将 grant 持久登记；不执行命令。
2. 准备执行：返回冻结清单及 `allowed / denied / stale / unknown / host-unavailable` 和原因；只有 allowed 可申请 Core 派发。
3. 派发前复核：在 R1 条件提交中检查状态版本、Stop、精确请求、写入权、grant 当前有效性和预算；持久登记意图后，由执行适配器再次核验实际目标和约束，保存启动观察与终态结果。

真实目标在计划评估、执行清单冻结和实际副作用前均解析。工作目录、程序、输入、输出及 cleanup 目标都核验最终链接目标；不存在的输出核验最近已存在父目录并限制创建范围。检查后若路径、链接、内容或策略改变，旧清单不得继续。源码/测试写租约保护受管写者；它不防御外部进程。宿主须提供足够的隔离或稳定目标访问；无法封闭检查与使用之间的风险时返回 host-unavailable，不能声称仅 EvalSymlinks 已消除竞态。

## 3. 授权、预算与恢复的分工

grant 表达允许范围；Core 请求账表达实际使用，两者不互相代替。范围批准可覆盖多次仍适用的执行，但每次都要通过独立的请求预算和 Stop 检查。专门恢复额度不能因重新批准、重启、换模型或重建索引而重置。

| 情况 | 确定性动作 |
| --- | --- |
| grant 未落盘/拒绝/解析未知 | 不派发；保存相关缺口，不能自动降级为旧授权路径 |
| 意图存在而启动结果未知 | 保留写入权及预留额度，对账同一请求；不重跑、不认作模型缺陷 |
| 可证明未启动 | 在原请求账释放预留；新派发仍重检授权/Stop/预算 |
| 结果存在但未消费 | 校验身份/输入/摘要并一次消费；不再执行、不重复计数 |
| LOG/grant 保存失败 | 对账原写入；使用所属阶段 SW07 的原恢复额度，不新增模型调用 |
| 后续撤销或 Stop | 阻止新副作用；已在途先观察/按宿主安全取消能力处理，不擦除既有事实 |

旧 schema 1 计划继续精确匹配 check_id/argv/目录/超时/profile/环境；未 consumed 的旧批准最多按原规则使用一次，consumed/stale/unknown 保持原限制。不把历史人工批准转换为 AI 批准，也不生成追溯 grant；新链若需范围发现必须有新的 AI 决策。旧使用事实经 R1 迁移保留，未知预算保持 unknown。保留旧文件，未来版本只读拒绝相关写入。

## 4. 本地交付与 AIW cleanup

交付计划冻结接受引用、Task/父分支及双方提交 ID、Task 工作区绑定、可提交路径及内容摘要、允许动作和预期前后状态。每个动作拥有稳定 action_id 并采用 R1 意图/观察/消费协议。只暂存清单内路径，已有索引含范围外改动即停止；不能使用 add --all 吞入无关改动。Git hooks、过滤器和签名程序等间接执行属于实际副作用检查，未知或宿主不允许时停止。

commit/分支创建/merge 各步重检计划适用性，保存产生的提交 ID；父分支移动或计划外变更须重新评估，计划声明的自身前一步结果以 action_id 关联，不重复审批既定步骤。冲突保留现场；不自动增加 abort、reset 或其他未列动作。未知时用提交 ID、父子关系、索引及工作区事实对账，不能仅凭提交消息判定已执行。push、Agent 直接删除、PR 和 archive 始终不在此链授权范围。

cleanup 使用单独 managed-cleanup 决策，绑定交付计划、精确工作树路径/分支、已合并提交与父分支；可与交付计划一起评估，但有独立条目。AIW 内部服务执行以下顺序：

1. 核对当前无在途写者、归属与登记工作树一致、合并祖先关系有效、目标不是 primary/父分支，且没有未纳入交付的本地内容。
2. 将辅助任务引用的必需输入封存在 Task 持久目录并核验摘要；来源清单缺失或引用未知则等待。E05 尚未提供可证明完整的来源清单时不清理，不妨碍 E02 其余部分开发。
3. 持久登记 worktree 移除意图，由 AIW 执行已有受管移除动作，观察实际不存在后才解除当前绑定；历史绑定、授权和交付事实仍保留。
4. 重检分支 ID/提交、祖先关系及其他工作树引用后执行受管分支清理，保存完成观察；不强删、不递归删除猜测路径。

每步恢复先检查原目标和已保存事实；缺失目标只有能与该清理请求匹配时才视为已完成。未知目标不清理，已 merged 不重新 commit/merge。R3 的辅助资源政策未闭合不会自动扩大清理权限。

| 责任 | 必须产出的契约 |
| --- | --- |
| E02 | R1 持久提交/系统锁/迁移；阶段、Stop、串行写入权、派发和恢复账；调用确定性授权核验；条件提交 Core 接受引用；受管分步交付/cleanup |

| E04 | 按 stage_request_id 去重的预留/消费/释放与失败归因；各专门预算及跨重启余额；为 E02 提供同一次条件提交中的预算变化 |

接受候选固定报告/输入摘要、Compile/Test run ID、计划/grant/政策及 N/A 依据。E02 在同一状态版本下复核当前输入、终态和必需证据，再保存不可变接受工件及 Core 引用并释放依赖；E03 不单独关 Work Item，E04 不在旁路计次。任何相关输入变化使候选失效。历史 waived 不满足必需测试。

开发顺序为 E02 → E03 → E04；E02 可定义并实现这些内部契约，E03 补执行适配、E04 补预算策略，缺少提供方时新路径保持不可派发。不得单纯将 schema_version 改为 10 就启用 E01 的冻结输入路径。E01–E04 全部实现、旧事实迁移完整、R1 平台证据与 R2 授权/接受场景验证齐备后，才通过同一受管启用边界切换。交付 cleanup 另等完整来源封存证据。
