# 自动化开发工作流设计

## Context

来源为 [已批准 Plan](../../../docs/requirements/REQ00001-workflow-automation/requirement-plan.md)、[原始软件需求](../../../docs/requirements/REQ00001-workflow-automation/software-requirements.md) 和 [工程交接](../../../docs/requirements/REQ00001-workflow-automation/engineering-handoff.md)。本设计对应九个 capability delta、SW01–SW34 和同号 AC，不再使用“生成 OpenSpec 工件”的通用示例。

当前基线：Workflow Core 持有 Work Item/Attempt/Gate/证据和写租约；execution 负责监督与派发；Session 保存 prompt/turn/输出；Task metadata 在 `.ai/<id>/`，OpenSpec 清单在 change 目录。现有 `Store.UpdateWithEvent` 和原子写工具是集成入口，但不能据其名称推定跨文件事务已成立。

本设计是需求驱动的工程方案，使用 fd-workflow 受管模式。用户于 2026-09-18 选择 R1 方案 A：本机磁盘优先、保留文件 Store、分阶段恢复；随后选择先闭合 R2，再授权按建议补齐 R3/R4。R1–R4 设计现已闭合；对应 Core Gate 仍须凭静态证据受管处理。实现依赖、运行验证和启用条件独立保留。

## Design Readiness

**FD_APPLIED（R1–R4；E01–E08 的设计输入）**。方案 A 已固定 R1 的持久化适配层、系统锁、兼容协议；其余见 [R2 授权契约](r2-authorization-design.md)、[R3 资源政策](r3-resource-design.md)、[R4 通知适配](r4-notification-design.md)。Task ID 与 change ID 均为 `workflow-automation`。规格更新位于既有 `.wt/workflow-automation`；Task 元数据及 Core 运行记录由主仓库 `.ai/workflow-automation/` 共享，不在 worktree 复制。设计闭合不代表实现完成、测试通过或对应 Core Gate 已自动解除。

用户已确认复用 Store 和受管执行入口，以恢复后的可观察状态、派发和预算作为验证边界。R2–R4 延续该边界，完成工程契约后同步设计证据；不授权运行测试、真实通知或 Git 交付。E02→E03→E04 的联合启用及 E05 先于 E06/E07/E08 后台消费的依赖保持。既有编号 checklist 和 Work Item 映射不变。

%% VALIDATION_PENDING: 方案 A 以当前 Windows 本机磁盘为实施和验证基线；网络盘、NAS、云同步目录没有相同可靠性承诺。目标卷、目录同步能力及真实故障恢复须在启用前取得证据；不能以用户选择 A 推定当前目录的实际介质已验证。

工作区静态对账：`task.toml.worktree/workspace_kind` 由 Task metadata 所有，Core 的 `workspace_binding` 保留已登记的路径与父分支；二者均指向既有 isolated worktree。`WorkflowRuntimeFromMeta` 只初始化缺失 Core，`RecordWorkspaceBinding` 不回写最初的 TaskReference，因此其中的 primary 是历史初始化值，不能单独据此改绑工作区。2026-09-18 的 `aiw task workflow diagnose workflow-automation` 仅报告 R1 Gate，未报告 workspace-binding-invalid。本轮保留原运行记录，以 metadata 与受管绑定共同校验实际写入路径；不通过手改 JSON 消除展示差异。

## Goals / Non-Goals

目标是让每次派发、写入权转交、授权、失败归因、接受和辅助处理都有固定身份、版本、预算与恢复规则；局部失败只暂停依赖它的工作。

非目标沿用 proposal：不增加第二套 Task/Session、不替代宿主权限、不执行自动 push/PR/archive、不自动批准知识，不以 Verifier 建立开发 Gate。产品未来的 AI 计划审批不构成本次工程会话的运行或 Git 授权。

## Decisions

### 1. 以 Core 接受事实作为唯一完成入口（E01–E04）

Attempt 保留整个实现项闭环；每次 Coder/Tester 生成和报告补交各有独立 stage_request_id，并绑定 Task、Work Item、Attempt、Session、turn、workspace、role、AISelection、允许路径和输入清单摘要。修复创建新阶段请求，不能改写旧请求以实现模型升级。

| 阶段 | 进入与责任 | 成功去向 | 失败/未知去向 |
| --- | --- | --- | --- |
| 输入准备 | 校验需求/验收/依赖和来源版本，冻结角色正文 | Coder | 必需来源缺失暂停相关派发 |
| Coder | 独占源码写入权，生成实现和报告 | 报告校验 | 请求结果未知先对账，明确缺陷归因后修复 |
| 报告校验 | Supervisor 核对绑定、字段、引用和输出版本 | Compile | 缺失/无效限一次仅报告补交；再失败人工处理 |
| Compile | 执行冻结的受控 Compile Plan | Tester | 实现缺陷回交 Coder；环境问题等待或按原额度恢复 |
| Tester | 编译适用且 Coder 写入权已安全释放；独立测试上下文 | 计划核验/Runner | 越界产物不接受；测试缺陷回交 Tester |
| 计划核验/Runner | AI grant 有效且范围/实际目标/宿主约束成立 | 接受检查 | 失败归因、未知对账、环境等待；不自行扩大权限 |
| 接受检查 | 当前报告、编译、必需测试齐备；N/A 有明确适用规则 | accepted、释放依赖、登记辅助 | 过期证据回到所需验证阶段，缺口不靠勾选关闭 |

全阶段优先检查持久 Stop、已有在途请求和未恢复写入。只有已保存终态或有证据的未派发/可安全重放才可重试。前台退出、超时或缺报告均不释放写入权。执行型 prompt/配置/脚本不自动归为纯说明文档；waived 不满足必需测试。

### 2. 报告、输入清单与证据分别保存（E01）

实现报告记录覆盖条款、实际变更位置/内容版本、接口和副作用、测试入口、理由、限制/风险与验证引用；未知、空和未验证分别表达，保留每轮历史。

输入清单按排序后的规范化路径/来源身份登记内容摘要、需求验收版本、计划/授权版本、相关配置/依赖和工具链标识。目录/fixture 发现结果进入单次执行清单；记录实际内容而非只记录 HEAD 或 Git 状态字母。实现、测试及相关配置变化使旧通过失效；无关日志、memory、展示时间变化不失效。

接受记录引用报告摘要、当前输入摘要、Compile/Test run ID 和适用性判定。下游只装载已接受且仍适用成果；Tester 可读取尚未接受的实现，但这不解除下游依赖。

### 3. 写入、派发和计次使用同一可恢复提交边界（E02/E04）

运行记录至少包含 schema_version、状态版本、阶段请求、lease_owner、dispatch_intent、dispatch_observation、结果引用、已用预算和 Stop。复用 Core 的 Task 排他写入范围，Stage、预算和租约的权威更新都通过 Store，不允许 CLI/Agent 直接写状态文件。

派发采用意图登记 → 实际调用 → 观察登记；预留额度在“确认未派发”时释放，在“已派发”时消费，未知保留预留并对账。不能把请求意图当成真实失败，也不能因重启重复消费。结果文件先保存，Core 再条件提交引用；崩溃后扫描同一请求结果并去重消费。跨文件原子性和故障注入边界属于 R1 闭合项，未证明前不可启用新状态机。

| 预算 | 固定计数键 | 上限及优先级 |
| --- | --- | --- |
| 报告补交 | 原生成请求 | 追加一次，仅报告 |
| 归因诊断 | 当前待归因失败 | 一次只读，仍不明转人工 |
| 基础设施恢复 | Work Item + 阶段 | 追加两次，确认无在途且条件恢复 |
| 模型有效失败 | Work Item + Actor + 实际模型档位 + 生成请求去重 | 每档两次后在下次合法派发时升级，每 Actor 最多两次升级 |
| 测试失败回交修复 | Work Item，Coder/Tester 共用 | 最多六次，第六次成功可接受，不派第七次 |
| memory/提取/汇总/Verifier | 操作类型 + 不可变来源身份 + 输入摘要 | 各追加一次，重调/重生成/重存共用 |
| 通知 | 通知事实 + 内容版本 + 冻结目标 | 首次 + 一次明确网络失败重发，60 秒等待 |

模型名称别名不代表升级；中间编译成功和另一角色活动不清零；报告、辅助、通知等专门额度不得叠加阶段恢复。旧预算无法重建时保留未知并集中展示缺口，不编造零余额或耗尽。相同历史输入被其他 Task 引用时复用同一辅助恢复账。

### 4. AI 批准计划，执行器确定性核验 grant（E03/E02）

将测试计划拆为“可授权计划”和“单次执行清单”。前者包含模块/真实路径范围、发现规则、命令模板/约束、资源和网络政策；后者固定当前匹配的测试、fixture、具体 argv 与输入摘要。grant 绑定前者及政策版本，执行证据绑定后者。范围内新增用例只改变证据，不重批计划；实质变化使旧 grant 不再适用。

授权由 AI 基于用户政策批准/拒绝，持久保存于 `.ai/<task-id>/grant.md`。每条记录具有独立 ID，并保留日期、权限、原因、是否同意、授权人类型（user/ai）、申请环节；补充计划摘要、政策版本、真实目标和范围以供确定性核验。人员身份和 user/ai 类型分开：需要记录人的操作时读取系统当前用户，不使用固定值 user 冒充姓名，也不把沙箱服务身份冒充未经核实的用户。

grant.md 使用有版本的结构化条目嵌入 Markdown，保留批准与拒绝历史；它是授权依据，索引只作可重建投影。写入必须在 Task 写锁内用临时文件+原子替换，并可靠落盘；损坏、版本冲突、未知字段或未落盘的同意一律不作为授权。恢复时检查请求引用的精确 grant 和计划，不靠文件 latest 猜授权。记录先成功再允许副作用；R1/R2 定义其跨记录提交与兼容验证。

风险规则核验实际 argv、工作目录、规范化路径和链接最终目标，不只按命令字符串判断。未知/禁止停止，危险变化需要新 AI 评估；AI 不能豁免 push、直接 Git 删除、宿主沙箱或网络政策。LOG 保存失败用所属阶段原额度恢复，不另行调用模型。

### 5. 本地交付和开发完成分开（E02/E05）

实际计划列明 Task/父分支、允许提交路径、动作、预期 Git 状态和受管清理目标，AI grant 只允许本地 commit、创建分支和本地 merge。执行前重新核对状态，存在无关改动不能全量提交；冲突/未知先对账，不能重放已发生副作用。

工作树和分支清理由 AIW 受管入口执行，校验归属、合并祖先关系和对应 grant。Agent 不能直接调用删除命令；允许 AIW 实现受管清理不表示允许一般删除。清理前封存仍被辅助任务引用的输入。primary/isolated 的现有隔离资格保持；自动流程不 push、不创建 PR、不 archive。

### 6. 以已提交事实恢复辅助队列（E05）

Work Item accepted 和 Task completed 的提交记录带来源版本；辅助处理使用这些持久事实的消费游标与固定输入键生成工作。接受/完成提交后若登记投影失败，下次从未消费事实补登记，不撤销完成，也不丢任务。

辅助队列记录 pending/running/reconcile/waiting/completed/unavailable、输入摘要、宿主身份、恢复余额及输出引用。前台离开后有界宿主继续已登记且有授权工作；没有可执行项时退出，保留等待项供后续启动恢复。Stop 阻止新派发，在途先对账；不承诺关机运行或开机自启。

Task 原始报告/决定为权威，memory 是带来源版本的投影。实质变化才登记摘要；发布采用预期来源版本条件写入，迟到结果不能覆盖更近期视图或人工原文。摘要失败而原始资料齐全时降级，资料缺失只阻塞依赖它的派发。

### 7. 知识以条目版本审阅与选择（E06）

知识条目版本固定正文、来源版本、证据性质、范围、使用方式和失效条件；人类编辑生成新候选。候选、已确认、待复核、已拒绝、已废弃为版本状态；只有人工可确认/拒绝/废弃及建立替代关系。替代不是废弃前提，同一拒绝输入不能换 ID 绕过。

汇总保存覆盖集合及各来源成功/失败/缺失状态，允许部分草稿。补齐产生新汇总版本，但不变条目的版本与确认保留。审阅请求携带所见版本做条件提交，冲突返回当前版本供处理而不覆盖。

失效检测同时在来源变化时标记和读取时复核；绑定内容、来源版本或范围实质变化产生新候选，即使结论相同。仅暂时不可读且恢复后内容未变可在原版本追加人工复核。排序、时间戳和无关文件变化不产生新知识版本。

选择按模块/路径/接口/领域标签匹配，显式优先级和稳定 ID 作为同分排序。已确认适用作为主参考；候选/待复核带警告且不能单独改变实现或验收；拒绝/废弃不注入。冲突时主需求优先，只有无法安全满足主来源/兼容/授权时才集中请求决定。确认知识仅产生同步建议，不自动改 CONTEXT/ADR/代码。

### 8. 通知只承诺文本发送尝试（E07）

复用通知 outbox 保存事实 ID、内容版本、冻结目标、纯文本、尝试次数、最近错误分类及 retry_due_at。事件去重使用事实与内容版本；重新渲染或时间戳不产生新发送额度。Task 完成事实保存后登记通知，不等待 Git/草稿/Verifier；普通进度静默，晚到重要结果关联原消息。

`aiw-notify` 使用统一请求/结果协议连接 console 与 Teams adapter。请求含消息 ID、文本、通道、目标和受管配置引用；结果区分 attempted、network_failure、configuration_failure、permission_failure、service_failure、unknown。对外发送状态只有已尝试/失败；内部排队、等待等是执行调度状态，不是送达声明。

console 输出视为本地尝试；Teams 调用 `send_teams_msg.py`，显式配置和环境凭据引用，验证 TLS，可配置可信 CA，不读隐式默认目标。凭据不进入 argv/日志。调用结果缺失、进程中断或无法归类的超时为 unknown，不自动当网络故障；明确 DNS/连接失败、连接重置等由 adapter 有据分类后才适用网络重试。证书、凭据、权限、服务拒绝为非网络类。没有查询/幂等/回执接口假设。

仅第一次明确 network_failure 安排 60 秒后一次重发，同一内容和目标；第二次不论结果均不再自动重发。崩溃恢复原 due time 和已用次数，不刷新；发送前重新检查 Stop、启用状态、提醒有效期及配置。主动禁用后不全量补完成通知；持续启用故障恢复只能续发仍符合次数和错误条件的消息。重复投递风险已被用户接受，不宣称 exactly-once。

### 9. Verifier 只读封存版本（E08）

在 Work Item 接受时封存原始需求/验收、准确 diff 基线、报告及验证证据，按固定输入登记独立只读调用。依赖开发结果不等待 Verifier。每个适用验收项记录判定、依据及缺口；有据不满足优先 failed，无明确失败但证据不全为 inconclusive，全部适用项有据通过才 passed。空报告/空覆盖和执行故障单独显示。

合法负面结论不算调用故障，不自动重新生成以求通过；只有 SW19 定义的调用/结果保存故障才共享一次恢复。晚到报告绑定封存版本，当前源码已变也不冒充审查了新版本；历史补审只读，不重跑测试或返工。

## Migration and Rollout

所有未完成 Task 先做无破坏读取和兼容投影，保留原记录、已用授权和不可解释事实。适用旧通过可复用；仅缺报告按一次补交；缺验证按当前有效授权补验证；旧 consumed 授权不恢复有效。预算缺口按 Task 汇总一次。

启用以 E01/E02/E03/E04 为一致性单元：不能启用新接受规则而仍沿用旧三次缺陷阈值。E05 的登记/恢复契约先于 E06/E07/E08 的后台消费。按组交付仍属于同一个 Task/change。

失败回退优先停止新派发、对账并保留证据；不将已接受的新记录降格为旧的缺证据完成旁路。不自动删除新格式或过期工件。具体版本转换和向后读取策略必须随 R1 闭合，不把文档中的兼容承诺当成迁移已通过。

## Engineering Readiness

### R1 持久提交与版本兼容方案

#### 当前代码证据与职责

静态基线为本 worktree 的 `internal/workflow/store.go`、`model.go`、`automation.go`、`execution/session.go` 和 `internal/repo/root.go`：

- `UpdateWithEvent` 已在 Task 锁内保存含 PendingEvent 的状态、追加事件、再确认序号；`RecoverPendingEvent` 只恢复原事件，不重做调用者操作。保留这一入口和包边界。
- `atomicWrite` 使用临时文件、Close 和 Rename，`appendEvent` 使用追加写；两者尚无显式 Sync，不能据此认定掉电后的持久顺序成立。事件逐行解析也不等于已经支持截断尾部恢复。
- 当前 schema 为 9；1–8 的归一化只是升级版本值及补默认值，不能据此补造新授权、预算或请求身份。
- 当前派发标记与实际执行结果是不同事实；Session 校验允许较新的 turn。新协议必须按精确阶段请求绑定结果，不能仅凭 DispatchedAt 或 Session latest 接受结果。
- 文件锁采用排他创建；文件锁残留与工作区写租约分别处理。不能仅凭超时、锁文件存在或前台退出判断旧执行器已终止。

Core 是阶段、请求、租约、Stop、预算、接受事实及消费游标的权威；grant.md 是授权依据，报告、输入清单和结果是有摘要的不可变工件。事件日志保留审计事实，但当前 Event 不包含完整状态差量，不能从它擅自重建丢失的整个状态。Session、task.toml 展示及 OpenSpec checkbox 均不是执行成功依据。

#### 最小数据契约

拟将运行状态从 schema 9 升至 10；实际实现若基线已有其他版本变更，必须先显式协调版本，不能复用含义不同的版本号。结构版本与每次提交递增的 state_revision 分开。新协议至少保存：

| 记录 | 必需绑定与用途 |
| --- | --- |
| 状态提交 | schema_version、state_revision、commit_id、预期前版本、PendingEvent 和已确认事件序号；恢复同一提交不再次递增逻辑版本 |
| 阶段请求 | stage_request_id、Task/Work Item/Attempt、精确 Session/turn、角色、workspace、输入摘要、模型选择、计划与 grant 条目版本、lease generation |
| 派发事实 | intent、执行器身份、observation、未派发/已派发/未知结论及依据；未知不是失败 |
| 预算账 | 预算类别、固定归属键、请求 ID、预留/消费/释放与归因依据；有效失败和调用额度分开记账 |
| 工件引用 | 工件类型、不可变 ID、内容摘要、来源版本及读取状态；路径或 latest 不构成身份 |
| 接受与辅助 | 接受/完成事实 ID、固定输入引用、辅助去重键、来源账本归属、恢复账、消费游标和条件发布版本 |

grant.md 保留完整批准与拒绝历史，每个条目版本不可变；状态保存条目 ID/摘要、计划和政策版本，索引只作投影。记录格式和真实目标检查由 R2 定义，R1 固定顺序：授权条目可靠落盘在前，Core 提交该精确引用在后，执行前再核验。单纯保存一条同意不构成派发许可，拒绝和失效记录不能因索引陈旧而被忽略。

#### 写入与提交顺序

方案 A 的平台接缝固定如下，作为 E01/E02 的实施输入，不再要求先完成实现验证才能写代码：

- 在 workflow 包内部封装持久替换与 Task 锁适配层，继续由 Store 调用；不增加数据库或改变外部 CLI。Windows 使用现有依赖中的系统调用包装，优先复用已经声明的 `golang.org/x/sys`，不为本方案下载或升级依赖。
- 持久替换采用同目录临时文件 Write → File.Sync → Close → Windows MoveFileExW 的 REPLACE_EXISTING / WRITE_THROUGH 替换 → 重新打开目标并 Sync / Close。事件追加也要检查 Write、Sync 和 Close 的错误。不得跨卷复制或先删除原文件；替换后的错误属于提交结果未知，必须对账。WRITE_THROUGH 或目标 Sync 不能单独冒充所有文件系统的目录持久性证明，目标卷的实际能力作为启用证据核定，能力不足则停用新持久执行协议。
- Task 锁改为稳定锁文件上的 Windows LockFileEx 排他锁，使用非阻塞竞争语义；锁拥有者持有句柄，离开临界区时 UnlockFileEx 并关闭。文件本身不因释放锁而删除；取得系统锁才代表排他，文件存在不代表进程仍在运行。源码写租约保持独立，不随文件锁释放而清除。
- 从旧 O_EXCL 协议迁移只在受管维护边界进行：先禁止旧协议的新写入，证明旧 Store 写入者已经退出，再在原排他范围内记录锁协议版本并切换；不能把遗留锁直接按新协议打开后就视为已取得旧写入者的权利。不明旧锁、旧版本写入者或在途源码执行均先对账。新协议保留稳定锁文件，使旧 O_EXCL 写入入口失败关闭，不能混用两套锁。
- E01 可以实现工件、身份与输入版本契约，但新接受、自动派发和迁移启用仍受 E01–E04 一致性边界及实际验证证据约束。其他平台保持既有行为；未经等价能力验证，不启用本方案的新可靠性承诺。

1. 在同一 Task 排他范围内检查预期 state_revision、未决提交、Stop、请求身份、写入权和授权。初次创建、迁移及修复也必须经过同一排他边界，不能绕开 Store。状态变更回调不执行外部副作用。
2. 先写输入、grant 或结果工件：同一目标目录临时文件，完整写入并同步，关闭后以平台已验证的替换原语发布，再完成该平台所需的目录项持久化。任何一步失败或提交结果未知均不报告可靠保存，不允许以删除旧文件后重命名作为降级实现。
3. 以一个状态提交同时保存关联的阶段、预算、租约、结果引用或消费游标及 PendingEvent。状态替换也遵循上述落盘契约；不能将多次独立文件写称为跨文件事务。
4. 追加并同步同一个事件，再可靠保存已确认序号并清除 PendingEvent。恢复只补齐同一个 commit_id；发生错误时调用者先重新读取并对账，不能假定提交未发生而重新派发。
5. 仅在所需提交已可靠完成、当前授权及 Stop 等前置条件成立时请求执行器启动。外部启动不能与文件写原子化；意图与实际启动之间的窗口一律通过观察和对账处理，不宣称外部 exactly-once。

Task 文件锁只保护短时记录更新，不跨整个 Agent 运行持有。源码写入权由持久租约及请求 generation 控制；恢复进程不得仅删除残留锁后转交源码写入权。清除残留锁需要验证原锁拥有者及进程代际已终止，并在排他恢复入口重新检查；无法证明则等待，不使用 PID 或锁龄单独判定。执行器仍可能在途时，即使文件锁已安全恢复，源码租约也保持。

#### 崩溃窗口与恢复矩阵

| 中断窗口 | 唯一允许的恢复行为 |
| --- | --- |
| 临时工件未完整发布 | 不建立引用、不派发；保留已存在旧工件及故障事实 |
| 工件或 grant 已发布，Core 未引用 | 按请求和摘要识别未引用工件；不得据此自动接受或执行 |
| 新状态与 PendingEvent 已落盘，事件未落盘 | 恢复同一事件；不再执行状态变更回调、计次或外部操作 |
| 事件已落盘，确认状态未落盘 | 核对序号、commit_id 和内容，确认已有事件，不重复追加或推进版本 |
| 事件存在截断尾部或同序号冲突 | 保留原文件并阻止相关推进；只有可证明为末尾未完成写且与唯一 PendingEvent 对应时，才通过受管修复从完整前缀重建；冲突、中段损坏及无法证明的缺口不猜测 |
| 派发意图已落盘，执行器观察未知 | 保留预留和源码租约，对账同一请求；不得把未知当成未派发或有效失败 |
| 有据确认未派发 | 在原请求账上释放预留；重新满足 Stop、授权、租约和预算条件后才可派发 |
| 有据确认已派发 | 去重消费对应调用额度；有效失败仅在结果和归因成立后计入模型/修复账 |
| 结果已保存，Core 未消费 | 验证精确请求、输入版本、摘要和终态；一次提交结果引用、归因、预算变化及消费标记，不重跑执行器 |
| Core 已消费结果，Session/展示投影未更新 | 从 Core 修复投影，不再次消费；迟到的不同输入结果只保存历史 |
| 接受/完成已提交，辅助队列未登记 | 按持久来源事实与固定键补登记，登记和游标推进在同一次来源 Task 提交中完成；不撤销接受 |
| Stop 或预算事实保存时返回未知 | 对账当前提交；禁止靠重启解除 Stop、刷新额度或重做副作用 |

辅助恢复账归属原始来源 Task：同一操作类型、不可变来源身份和输入摘要只指向一份账。其他 Task 引用该来源时携带 source_owner_task_id 与固定键，不复制恢复余额；原账不可读则标记辅助不可用，不能以新 Task 建立零计次替代账。来源 Task 的受管存储保存该账及持久来源事实，Session 或 worktree 清理不能删除仍被引用的权威事实。跨 Task 发布只提交可重建引用，执行额度只在来源账本中预留和消费；不以两个 Task 文件同时成功为前提。此处冻结恢复所有权，具体调度仍属于 E05。

#### 兼容、迁移与回退

- 旧 schema 1–9 先只读解析，保留原字节、来源版本和摘要；不得在 Load 时将缺失的新字段填成有效授权、零失败或已接受。
- 迁移前先处理旧 PendingEvent、在途事实及持久 Stop，再在 Task 锁内生成 schema 10 状态。旧快照先可靠保存；新提交引用迁移来源和固定迁移 ID。中断后恢复同一迁移，不重复创建运行事实。
- 旧已用/consumed 授权保持已用，适用旧结果按当前输入和证据规则复用；仅缺报告使用原请求的一次补交，不能借迁移新增额度。无来源证明的预算保留 unknown，集中形成 Task 级缺口，不能伪造零余额或耗尽。
- 不识别的未来 schema、授权字段或必需记录版本保持原件并禁止相关写入/派发；不通过 JSON 忽略字段后重新序列化丢弃未知事实。grant 的确定性解析仍依 R2。
- 旧二进制不得写新格式；回退先停止新派发并对账，保留新事实，不能恢复旧快照继续执行以绕过已用预算或新接受规则。
- E01/E02/E03/E04 的新接受与预算规则一同启用；E05 的来源登记和恢复协议先于辅助消费者。分组开发不表示可单独启用半套接受规则。
