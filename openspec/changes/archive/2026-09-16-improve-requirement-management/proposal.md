# 完善 Requirement Management

## Why

当前需求管理能组织对话和保存工件，但没有可靠保证把已有需求、项目背景和支持 Skill 方法交给模型。用户感受到追问不够专业，需求容易在关键规则、异常情况和验收条件尚未明确时进入汇总。

优先完善需求发现与上下文链路，不等待完整知识库、Supervisor 多角色调度或模型升级。

## What Changes

- 序号缺失或损坏时，根据现存活动、归档及取消需求恢复编号；损坏原件先备份，恢复结果明确提示，读取失败不得当作空目录。
- 正式需求工件统一存入 docs/requirements，运行状态与临时文件存入 .ai/requirements；不兼容旧路径、不提供迁移命令，当前项目的现存需求直接移动，保持需求身份与正文不变。

- 每轮构造可追溯的需求上下文，实际装载需求工件和选定讨论方法。
- 使用通用需求发现维度，并按领域按需补充方法，不把非金融需求默认套入金融流程。
- 维护有来源的需求覆盖判断，按重要缺口提出 1～3 个问题。
- 根据新回答和确认后的工件重新判断阶段，而不是仅检查文件是否存在。
- 恢复会话时重建已确认事实、未决问题和讨论进度，避免依赖模型线程记忆。
- 区分保存不完整草稿、建议批准和工程准备；保留显式人工确认。
- 保存输入来源与缺失信息，提供可控模型响应测试及固定案例人工评审计划。
- 为新需求自动分配 REQ00001-slug 格式的稳定 ID，统一 CLI 与聊天创建入口；保留显式 ID 创建和现有需求引用。

## Capabilities

### New Capabilities

- `requirement-discovery`：需求上下文装载、专业发现、阶段推进、恢复与就绪判断的行为约定。当前稳定规格目录没有可复用的同名能力，采用 ADDED requirements 描述已有入口上的新增约束。

### Modified Capabilities

- `requirement-management`：在现有生命周期能力上增加自动编号、显式 ID 兼容和编号分配约束。

## Impact

影响需求领域逻辑、需求对话命令入口、支持 Skill 路由和相关文档。Session 继续提供模型调用及记录能力，尽量不改变其通用契约。
不新增第三方依赖、网络检索、Git 操作或第二套生命周期；不包含实际功能实现。

## Problem Statement

用户希望 Agent 主动理解业务背景、识别遗漏与矛盾，并通过专业问题共同完善需求，而不是只整理用户已经表达的内容或推动确认保存。

## Solution

每轮先形成需求上下文，再选择相关讨论方法和最高优先级缺口，提出少量有依据的问题。回答形成候选结论，确认后才进入正式需求工件；汇总必须说明覆盖情况、证据和剩余决定。

## User Stories

1. 作为需求提出者，我希望已有需求内容自动进入讨论，避免反复解释背景。
2. 作为需求提出者，我希望恢复会话后从未决问题继续，而不是重新开始。
3. 作为需求提出者，我希望已确认规则被引用，不再被无理由重复询问。
4. 作为非金融项目用户，我希望使用适合当前项目的方法，不被金融模板限制。
5. 作为领域用户，我希望关键业务规则得到专业追问，而不是只填写通用字段。
6. 作为需求提出者，我希望 Agent 主动发现异常路径、边界和失败行为。
7. 作为需求提出者，我希望每个重要问题解释其影响，并提供适当选项及取舍。
8. 作为需求提出者，我希望每轮问题少而重要，不被完整问卷淹没。
9. 作为审阅者，我希望事实、推测和建议明确分开，并保留来源。
10. 作为审阅者，我希望矛盾被提出，而不是由 Agent 静默选择一个结论。
11. 作为需求提出者，我希望可以保存不完整草稿，但不被误报为已经就绪。
12. 作为决策者，我希望批准、保存和晋升仍由我明确确认。
13. 作为维护者，我希望能从对话记录检查 Agent 实际获得了哪些依据。
14. 作为后续设计者，我希望最终输出包含目标、范围、规则、验收实例和未决风险。
15. 作为需求提出者，我希望创建需求时只提供英文短名，由系统生成便于排序与交流的编号。
16. 作为旧脚本维护者，我希望能够显式指定原有 ID，且历史需求无需重命名。
17. 作为聊天用户，我希望确认创建后，后续讨论和正式工件始终关联实际生成的完整 ID。

## Out of Scope

完整知识库与语义检索、跨项目知识共享、自动模型升级、多 Agent 讨论、Supervisor 执行重构、单元测试自动闭环、通知发送、发布评审，以及修改本次无关的工作区变更。

## Further Notes

用户已确认允许在脏工作区创建 Task，并确认测试边界；随后请求实施本变更。见 design 的 Design Readiness。测试边界确认不代表授权运行测试或真实模型评测。
