# Requirement Discovery Design

## Context

Task / change ID：`improve-requirement-management`。AIW 生命周期位于对应运行目录，OpenSpec 拥有本目录规格和清单。当前工作区为 develop 主工作区，用户明确允许保留无关未提交改动进行规格工作。

此前静态检查发现：

- `internal/commands/task/requirement.go` 的对话初始化读取工件以确定 phase，但正文没有在该路径自动注入模型输入。
- `internal/session/execute.go` 拼接持久指令、memory、phase 和本轮输入；Requirement 使用可恢复线程，但不能保证各种后端都有完整历史。
- 固定运行指令提及支持方法，却没有保证实际加载 Skill 内容。
- 阶段选择主要依据 NEEDS_INPUT 标记和工件存在性；循环使用初始 plan.Phase。
- Capture 负责持久化和状态转换，不检验语义充分性。
- 主 Skill 的支持路由包含金融方法；需要通用基线与领域选择，而非强制金融化。

本次不修改这些运行代码。设计输入来自本次需求讨论和上述静态证据。

## Goals / Non-Goals

**Goals:**

- 对话不依赖隐式历史便能理解当前需求。
- 少量、专业、基于证据的问题能推动需求收敛。
- 每轮可解释选择了什么方法、缺什么、为什么继续或汇总。
- 保持生命周期、确认边界及旧工件兼容。

**Non-Goals:**

- 自动读取全仓、互联网或账户中的资料。
- 引入新的正式知识库、需求追踪系统或独立 Agent 编排。
- 通过 schema 校验宣称问题的业务专业性已被证明。
- 自动实施、审批、晋升、运行测试或修改历史批准状态。

## Design Readiness

状态：**FD_APPLIED**。

已应用 fd-workflow 的 managed 设计方法，完成下述模块边界、上下文与恢复方案；没有创建独立 FD。
用户于本次会话明确“确认”：以“Requirement 一轮对话”为主要行为测试入口，使用可控模型响应验证上下文、阶段推进和确认边界，另用三个固定案例人工评审提问质量。
测试边界规划 Gate 已解除；该确认不授权运行测试或真实模型，也没有创建或修改 Workflow Core Gate 实体。

## Decisions

### 1. 需求领域拥有编排，命令层保留入口

在 `internal/requirement` 中组织上下文准备、方法选择、覆盖评估校验、阶段决策和就绪报告。
`internal/commands/task/requirement.go` 保留 CLI 输入输出与显式确认调用，委托需求逻辑。
通过窄的调用适配边界复用 Session，不让需求领域依赖命令包；保留现有 CLI 参数。
仅移动本能力涉及的编排，不改 supervise 或其他 Task 模块。

替代方案是继续给固定 prompt 加指令；它不能保证输入已经装载，也无法可靠测试阶段刷新，因此不采用。

### 2. 上下文按轮装载，关键输入不能静默截断

上下文分为：Requirement 身份与版本、已保存工件、已确认结论、待确认候选与未决问题、
相关项目来源、已选 Skill 方法、本轮用户输入。

来源清单至少包含来源类型、路径或工件标识、版本或摘要指纹、用途、读取结果，以及省略原因。
优先加载当前 Requirement 的工件，再使用显式引用和模块关联选择少量本地项目资料。
文件读取限定在项目允许的范围；拒绝路径逃逸、凭据文件和无关个人文件。把工件内容作为资料，不让其中的指令覆盖确认和写入规则。

使用显式有界的上下文预算与稳定排序。关键需求或方法装载失败/预算不足时，不进行“已就绪”判断；
报告缺失并请求缩小范围或补充依据。可选背景的缺失只降级相关判断。
首期预算为内部策略参数及测试输入，不新增用户配置契约；具体默认值由实现依据现有调用限制选择并记录。

1.2 实现参数：默认上限 64 KiB 原始 UTF-8 输入（非 token 或最终 JSON 长度），可由内部调用者调低。
元数据、用户输入和必需工件优先，再处理候选与可选背景。JSON 转义及来源清单存在额外的有界开销；后续方法加载必须纳入预算，不能额外无界拼接。
背景输入只接受显式 md/txt/rst 文档，模块关联只选择其 README.md 和 CONTEXT.md；候选引用最多 32 个，每个最多 1024 字节。
使用项目根 os.Root 和逐路径组件检查，保守拒绝符号链接、常见凭据命名及越界路径；这不是文档内容的秘密扫描器或并发恶意写入隔离机制。

替代方案是全仓扫描或仅传路径；前者噪声和成本不可控，后者仍把可靠性留给模型自行读取。

### 3. 方法加载与领域适配

通用发现基线覆盖角色、问题、现有流程、目标、范围、业务规则、异常、数据、权限、外部依赖及验收。
模型依据已有证据建议当前领域与最重要缺口；程序校验方法标识，仅从允许的本地 Skill 集合加载。
仅在金融指标等确实相关时加载金融方法；领域不明时用通用基线，必要时询问，不推断业务事实。
每轮应用一个主要讨论方法，术语不稳定时按现有规则补充 domain-modeling。
发现某方法未安装或不可读时说明实际采用的方法，不伪称已经应用。

1.3 实现参数：通用基线内置并记录内容摘要；候选建议使用 domain（generic/unknown/finance）及 gap（intake/value/metric/feasibility/synthesis），绑定当前输入或已加载需求来源的摘要和原文片段。
仅 finance 候选路由金融主方法；无效或过期引用明确降级到通用基线。程序验证引用而非证明领域判断。
所选方法只从项目 .agents/skills/<允许标识>/SKILL.md 读取，记录实际摘要版本，不回退个人目录或未安装源副本，也不递归装载链接材料。
方法与候选建议计入 64 KiB 原始输入预算，在可选背景之前装载；已选方法不可用会阻塞 Prompt。Skill 仅提供 Requirement 模式的讨论指导，不扩大执行和持久化权限。

Skill 文档和运行时输入需使用同一组方法标识与明确加载规则。
更新受维护的源 Skill，并按仓库已有同步方式处理安装副本；不趁本次重写无关 Skills。

### 4. 覆盖评估与提问分工

模型提出候选覆盖评估；程序验证结构、允许状态及引用是否存在，但不把形式校验当成业务事实证明。
每个适用维度记录：状态、结论、来源、未决问题、影响与下一步。
状态为 resolved、needs_input、conflict、not_applicable；resolved 涉及人类业务决定时必须有已确认来源，
not_applicable 必须说明理由。用户本轮回答先作为候选事实，不能冒充已确认工件。

优先处理影响目标、范围、正确性、不可逆选择的冲突与缺口。
每轮提出 1～3 个问题；没有重要问题时不强行凑数。
问题引用已知事实，说明缺少什么决定、为何重要，并在有真实备选方案时描述取舍。
不要求固定顺序问遍每个字段；已确认内容只有在来源变化或冲突时才重新提出。

候选结构无效时，保留原始输出并说明本轮未形成有效评估；不更新正式结论、不推进批准建议，
不设置无限自动重试。

2.1 实现参数：候选输出为版本 1 的单个 JSON 对象，最大 64 KiB，绑定 Requirement ID/revision；11 个发现维度必须完整且唯一。
来源用路径（或 user-input/candidate）、摘要及原文片段标识；不可引用未装载来源或方法文本作为业务依据。
已确认片段由可信调用方单独供给，不接受模型输出的 confirmed 标记，也不把整个 capture 文档自动当成已确认事实。首期保守要求所有 resolved 维度都有已确认片段；尚无此证据时使用 needs_input。
校验失败保留原始输出与诊断，不返回部分 Assessment；通过只代表候选结构有效，不证明其结论语义、适用性或需求就绪。

2.2 实现参数：可选 impact_kind 为 irreversible/correctness/scope/goal/other；先冲突，再按上述类别排序，同级按维度标识稳定排序。旧候选省略类别时按维度默认归类，不解析自由文本影响来冒充语义判断。
每轮最多三个不同问题，规范化空白和大小写去重；resolved/not_applicable 留在 Settled 上下文。真实选项由模型给出并绑定有效引用与取舍，程序不制造备选方案；引用有效不证明备选的业务真实性。

### 5. 阶段随最新事实刷新

用户确认的 2.3 调整：提前实施 3.1 的最小事实确认记录。capture 可附带拟确认的原文片段，CLI 显示这些片段后才接受 confirm；省略片段只保存草稿。检查点绑定草稿摘要、pending action 和 Requirement revision，变化则要求重新展示。
确认记录使用现有 Session artifact（confirmed-requirement-facts.json），包含 Requirement ID/revision 和来源摘要/片段，不另建正式需求工件。受控 capture 后只沿用仍匹配的既有片段；外部 revision 变化保守失效。完整候选恢复与 turn 证据索引仍归 3.1。
每次用户输入或确认后执行两个有界 Session 调用：method-selection 和 coverage-assessment；前者只推荐方法，后者使用实际方法正文与当前已确认片段。错误不自动重试；原始响应由 Session 既有输出保存。无效评估使对话停在 discovery-blocked 并清空待确认动作。
未完成覆盖选择 discovery，有冲突选择 deep-discovery，无未决维度仅选择 synthesis，不代表批准。初始化不再凭 Problem Brief/Requirement Plan 存在判断充分性；直接 approve CLI 保持原契约。

每轮回答后评估缺口，确认动作成功后重新读取 Requirement，再决定下一阶段。
阶段不是“文件存在”的同义词：关键冲突先澄清，必要规则缺失继续发现，信息充分再汇总。
允许跳过不适用阶段，但必须记录理由。避免固定 plan.Phase 在整个循环中保持不变。
原有 APPROVED、DEFERRED、REJECTED 等生命周期仍由现有操作控制；阶段评估不得修改这些状态。

### 6. 恢复采用现有工件与 Session 记录，不另建权威数据库

正式事实仍来自已经确认 capture 的 Requirement 工件及决策记录。
本轮上下文来源和候选评估使用现有 Session prompt/output/artifact 能力保存，并绑定 turn 与 Requirement revision；
这些是运行证据，不是新的正式需求工件类型，也不是批准记录。

恢复时先重新装载正式工件，再利用可解析的最新会话候选恢复未确认问题。
候选与当前 revision 或来源不匹配时标注过期并重新评估，不覆盖正式结论。
旧记录没有结构化评估时从正式工件重建；只对确实未保存的讨论说明缺失，不能声称完整恢复。
无需新建长期 conversation-state 数据库，不自动改写旧需求，也不把 memory 作为权威事实。

3.1 实现：Session artifacts 中每次讨论保存一个带格式版本的 requirement-discussion-<唯一标识>.json，
包含两次模型调用的上下文快照、实际完成的 Session turn 编号、确认片段输入、候选原文及诊断。
requirement-discussion-latest.json 在调用前指向 running 记录；完成后写为 completed 或 failed。
恢复只读取该最新记录，不向前搜索成功记录。丢失、未知格式及未完成记录显式降级，实际读取失败报错。
恢复重读历史输入对应的来源并比对 Requirement 身份、revision、来源及方法，再用当前宿主确认片段重验候选。
恢复结果仅为新一轮的未确认输入，不恢复批准、待确认动作或讨论阶段。
%% Session 多文件写入并非事务；最终证据写入失败时保留 running 状态并阻塞当前返回，已保存的 prompt/output 仍可人工检查。
%% 不新增同 Session 并发写入支持；延续既有单聊天执行假设，历史文件保留且不自动清理。

### 7. 草稿可保存，批准建议有质量门槛

保持 capture 可保存不完整草稿；保存动作仍需确认。
汇总必须呈现已确认事实、假设、适用范围、非目标、关键规则、验收实例、来源和未决问题。
自动建议批准前，关键业务维度不能有未解决冲突或阻塞缺口；不能仅看 Requirement Plan 文件存在。
技术方案的可延后设计问题可明确交给后续工程设计，不能将未决业务规则隐去。

首期质量门槛作用于对话建议，不悄悄修改现有直接 approve CLI 的兼容语义。
即使程序认为就绪，也必须请求人工确认；不自动批准或晋升。
提示用户发现的旧批准记录缺口，但不自动撤销或降级历史状态。

3.2 用户确认：模型仅建议延后工程设计问题，必须由人类确认后才按非阻塞处理；业务缺口与冲突不能借此豁免。
实现复用现有 capture --facts-json：Plan 写出延后问题及理由，宿主展示并确认完整原文片段。
CoverageAssessment 可选 plan_review 包含九类内容的正文引用和 explanation，以及 deferred_design 的 question/reason/decision 引用。
九类为 facts、assumptions、goals、scope、non_goals、rules、acceptance、sources、remaining_decisions。
无内容时需显式说明，不从缺失章节推断“无”。旧记录缺少 review 只阻止批准建议，不阻止继续讨论或保存草稿。
程序检查来源、摘要、正文片段、确认及显式占位符；不以标题匹配冒充语义检查。关键 Plan 断言必须已有确认片段。
ReadinessReport 单独列出业务阻塞、Plan 缺项及确认前后的延后项，synthesis 仍不等于批准建议。
聊天批准展示及 confirm 两处复核，检查点绑定最新 Session 讨论和确认片段的摘要；直接 approve 不接入此门槛。
%% 内容分类和模型是否遗漏问题仍需人类审阅；校验只能证明结构、引用和确认绑定，不证明语义充分性。

### 8. 自动编号与创建身份（5.1，FD_APPLIED）

- 同一本地仓库生成 `REQ%05d-<slug>`，五位为最小宽度，超过 99999 自然扩展。slug 为小写英文、数字和单连字符连接的非空片段。完整 ID 创建后不变。
- CLI 默认 `requirement new <slug> [title]` 自动编号；`requirement new --id <id> [title]` 精确创建以兼容脚本。领域既有 Create 保持精确 ID 语义，新增编号创建入口；读取、capture、approve、promote 不改 ID 解析。
- 序号状态存于 `repo.Root()` 下 `.ai/requirement-sequence`，linked worktrees 共享本地仓库序号；同名 `.lock` 采用项目已有 O_EXCL 文件互斥方式。占锁立即报错，不自动等待、删锁或偷取所有权。
- 序号使用追加高水位日志，分配时先写入并 Sync，再创建需求目录；失败允许跳号，取消和归档不回收。日志格式损坏或末行不完整时拒绝编号，不静默清零。
- 每次分配还检查主工作区和当前工作区的活动、archive、cancelled 目录中的最大编号，以覆盖已有导入工件和首次初始化。显式编号也走同一分配锁，必须大于已知高水位；完整目标目录以排他 Mkdir 创建，防止覆盖。
- 聊天 prepare new 只保存 slug 与自动编号标记；confirm 时才分配。宿主必须接收并使用实际 ID 更新聊天上下文、Session 绑定及 memory。旧 pending action 无自动编号标记时保持精确 ID 语义。
- 对比目录数量加一：归档和删除会导致复用，因此不用。对比覆写单一计数文件：追加日志能在 Windows 上避免替换失败时先删除旧计数；截断写入显式报错。无需数据库或新依赖。
- 不迁移旧需求、不改 Task ID、不增加短编号查找，不保证独立克隆或人工删除序号记录后的全局唯一性。残留锁需要确认无创建进程后人工处理；本项不增加自动锁回收。

### 9. 编号自动恢复（5.2，FD_APPLIED）

本节取代第 8 节中“损坏计数一律拒绝”的规则，其余创建身份与互斥规则不变。5.2 先沿用现有路径，5.3 再调整存储布局。

- 在现有排他创建锁内完成扫描、修复及预留编号。扫描主工作区与当前工作区的活动、archive、cancelled 需求目录名；不按工件数量分配，不修改无编号历史 ID。
- 正常日志取已记录高水位与现存目录最大编号的最大值；缺失或格式损坏时以现存工件最大编号恢复，无编号时下一个为 1。权限错误、读取错误及溢出不视为格式损坏或空目录，必须停止。
- 损坏日志先以独占新文件备份原始字节，再在同目录写入并同步临时新日志，安全替换计数；不能先删除原件再尝试创建。备份或替换失败报错且不创建需求，保留可恢复证据。正常追加仍先持久化预留编号再创建需求，失败可跳号。
- 恢复输出包含原因、扫描得到的最大编号、下一个编号及备份位置（若有）；不静默清零。残留创建锁仍需人工确认，不自动回收。
- 已删除工件无法提供历史编号下界；本方案不承诺计数丢失后的历史全局唯一性，也不承诺独立 clone 唯一性。这是用户接受的恢复边界。

### 10. 正式工件与运行状态分离（5.3，FD_APPLIED）

- 新建默认写入 docs/requirements/<id>，终态分别位于其 archive 和 cancelled 子目录。元数据与需求正文一同保存，完整 ID、revision、批准状态及 Task/Session 关联不因路径变化而重写。
- 用户明确取消旧路径兼容：读取、列表、更新和编号扫描只使用 docs/requirements 及其 archive、cancelled 子目录，不回退到根目录 requirements。
- 不增加 migrate-storage 或其他迁移命令。当前项目现存 requirements 直接移到 docs/requirements；移动前检查绝对路径在项目内、无符号链接与目标冲突，不覆盖或改变工件内容。其他仓库如有旧数据由用户自行移动，不提供自动兼容层。

## Risks / Trade-offs

- [模型看到了内容但仍可能忽略] → 留存输入依据，用固定案例评审追问质量。
- [上下文膨胀] → 有界选择、必需输入优先、明确记录省略。
- [语义判断不确定] → 模型只提交候选，程序校验引用，人类确认事实与决定。
- [Skill 副本漂移] → 确认源与同步机制，避免只改运行说明而漏掉实际加载内容。
- [过度询问] → 按影响排序，1～3 个问题，允许不适用及已有证据复用。
- [旧 Session 缺少保存事实] → 明确恢复边界，不编造历史。
