# Issue Plan：capture 成功后清理源草稿

- Issue：`ISSUE-00009`
- 日期：2026-10-18
- 状态：用户明确授权 approval、promote 和 fd-workflow auto；本版作为批准来源，由 CLI 记录审批和 FD 关联。
- 提出者：当前用户；整理者：Codex。

## 问题与目标

用户发现 `aiw issue capture` 后临时草稿继续留在 `.ai/issues/drafts/`，认为成功捕获后应清理以减少垃圾。本次文件转换需求讨论实际积累了多个中间草稿，正式内容已保存，临时文件仍存在。

目标：capture 成功保存正式工件及元数据后，默认删除本次已捕获的源草稿，使临时目录不持续积累已消费文件。此为独立工作流改进，不属于 `ISSUE-00008` 文件转换插件的实现范围。

## 静态事实与来源

- 用户明确意见：“capture后，就应该清理，减少垃圾。”
- `src/internal/issue/store.go` 的 `Capture`：读取源文件，写正式目标，更新工件摘要及 revision，再写元数据；成功返回前没有删除源文件。
- `src/cmd/aiw-req/issue-capture.go`：调用共享 Capture，成功后打印正式工件路径。
- `src/internal/issue/context_sources.go`：已有 `.ai/issues/drafts/` 与兼容 `.ai/requirements/drafts/` 的路径约定；该上下文读取保护不能直接视为当前 Capture 删除路径已有保护。
- 已静态搜索相关源码，未运行 capture 清理功能或测试。

## 建议业务规则

1. 正式工件与相应元数据全部保存成功后，才清理本次捕获的源草稿；任一步失败均保留源草稿。
2. 默认自动删除仅限当前项目 `.ai/issues/drafts/` 和兼容 `.ai/requirements/drafts/` 内的普通源文件。capture 允许其他来源时仍保留其原文件，避免将用户输入资料当成临时草稿删除。
3. 只删除实际成功捕获且内容未发生变化的那个文件；不递归清空目录，不按文件名前缀删除其他版本，不删除尚未捕获的草稿或其他 Issue 文件。
4. 删除前确认路径、实际文件身份与内容仍匹配本次捕获，防止符号链接、目录穿越或源文件被替换导致误删。具体原子性和实现方式由 FD 设计。
5. 若正式捕获成功但草稿删除失败，保留正式结果，明确报告“捕获成功，草稿清理失败”及残留路径；不回滚正式工件，不引导盲目重复 capture。精确 CLI 返回约定在设计阶段确定。
6. 原批准记录、正式工件、决策日志、显式历史快照不属于临时清理对象；旧 REQ 入口如共用相同 Capture，应使用相同规则。

用户明确要求 approval and promote，并用 fd-workflow auto 实现，确认上述范围与边界。批准不表示设计或运行验证已经完成。

## 非目标

- 不在本次讨论中删除已有草稿、修改源代码或开展运行验证。
- 不自动扫描清理历史目录；不清理所有未关联文件；不增加定时清理。
- 不修改 ISSUE-00008 的功能范围；不改变审批、promote 或 FD 生命周期。

## 验收示例

- 从项目草稿目录 capture 成功后，正式内容、摘要及元数据可读取，当前源草稿不存在，其他草稿不变。
- 从兼容草稿目录 capture 有同样结果。
- 正式工件写入或元数据保存失败时，源草稿仍存在。
- 源文件在 capture 期间改变、路径不在草稿目录或为不安全链接时，不误删。
- 删除失败时，正式结果仍在，并明确提示残留草稿和清理失败，不把部分成功伪装成全部失败或全部成功。
- 外部普通来源文件在 capture 后保留；正式目录快照与其他 Issue 草稿不受影响。

## 规模与后续决定

单一用户可验收结果，规模小到中等；难点是保存与清理的先后关系、路径和文件身份边界，以及清理失败的准确报告。暂不拆分；实现时使用独立编号 FD，不混入文件转换插件。

已确认：仅清理本次 capture 的项目草稿文件；不扫描删除其他历史草稿。

已确认：捕获成功但清理失败时，保留成功捕获结果并发出明确警告。Planner 采用兼容策略：保持 capture 的成功退出状态，在 stderr 报告清理失败及残留路径，不引导重复 capture；不新增部分成功退出码。
