## 来源陈述的事实与边界

来源将本批定义为工作流自动化的需求整合：每次实现、验证、接受及辅助工作的事实均须可追溯、可恢复且有界。原有稳定规格位于 `openspec/specs/`；本 Plan 不覆盖该稳定基线，也不声称现有代码已经满足候选要求。

来源记录共有 34 条软件要求（SW01–SW34）及同号验收场景（AC01–AC34）。验收矩阵明确标为“未执行、待取得证据”；文档存在、清单勾选或结构检查都不构成功能通过。

## 术语、角色与目标

- **Task** 是整体工作生命周期；**Work Item** 是可接受的实现项；**Attempt**、阶段请求、Session 与 turn 是不同执行身份，不能互相冒充。
- **Supervisor** 保存事实并按规则编排；**Coder** 实现；**Tester** 独立设计/维护测试；Compiler/Test Runner 产生受控执行证据。
- **AI 授权人**根据已确认的授权政策批准或拒绝初始测试计划及具体 Git 交付计划，并持久化授权记录。它是产品内的授权角色，不授权本次 Requirement 管理流程执行任何 Git 操作。
- Context Builder 与 Model Router 只组织输入、选择已配置模型。Task memory、知识提取/汇总、通知和只读 Verifier 是辅助能力，不能代替接受规则。
- 目标是形成可恢复的“Coder → 编译 → Tester → 授权测试 → 接受”闭环，给出可观察证据、跨 Session 上下文及可审阅知识；仅在缺少必要决定、危险/未知操作或无法安全恢复时请求人工。

## 范围

本 Requirement 的候选范围覆盖 R01–R10：

1. **报告、证据与兼容（SW01–SW04）**：每轮可追溯报告、确定性校验和单次报告补交；受控编译/测试证据有效性；未完成旧 Task 的安全复用与暂停。
2. **阶段、恢复与写入权（SW05–SW09）**：冻结阶段身份；Coder/Tester 串行写入；未知结果先对账；Stop 持久化；按归因有界恢复；预算跨重启可恢复；有界后台辅助工作。
3. **单元测试与接受（SW10–SW14）**：独立 Tester、由 AI 授权的初始测试计划、授权内发现、危险操作审查与 LOG、修复闭环，以及基于当前证据的接受判定。
4. **模型与预算（SW15–SW17）**：从已配置 Profile 路由、按实际生成请求归因、每档失败升级和 Coder/Tester 共享修复上限。
5. **Task memory 与辅助恢复（SW18–SW19）**：原始事实优先于 Session 投影，四类辅助工作按固定输入各有一次恢复边界。
6. **知识生成及治理（SW20–SW24）**：异步提取和汇总、部分覆盖、版本化五态审阅、失效/复核和人工文档边界。
7. **上下文与资源（SW25–SW27）**：保存实际角色输入、可复现知识选择、必需输入不可截断及有界历史回填。
8. **通知与独立审查（SW28–SW32）**：开发完成与交付/辅助结果分离；由 `aiw-notify` 发送纯文本、有限网络重试且不声称送达；固定版本的只读 Verifier 及 failed/inconclusive/passed 区分。
9. **横向约束（SW33–SW34）**：具体 Git 交付须有同范围的 AI 授权计划；本批采用一个 Requirement、一个后续 Task/change 生命周期，内部按 E01–E08 分组。

## 非目标

- 不授权集成/E2E 或第三方业务接口测试，也不把“端到端关系”理解为外部业务集成测试。
- 不提供自动语义向量检索、无差别历史全量补处理、自动批准知识/需求、Verifier 自动返工、永久后台服务或开机自启。
- 不因通知传输进入范围而扩大网络权限；本 Plan 不授权本次流程执行测试、网络请求、Git 提交/合并/清理、配置变更、Task 创建或推广。
- 产品交付中禁止 `git push`、任何直接 Git 删除、PR 与 archive；worktree/branch cleanup 仅能通过 AIW 生命周期操作且必须有对应授权记录。
- 不修改 stable spec，也不冻结持久化、索引、并发、恢复信号或外部协议参数等工程设计。

## 已确认政策决定

### 授权主体与授权记录

- 初始测试计划与具体 Git 交付计划由 AI 授权人自动批准或拒绝；User 只负责调整授权政策，不参与逐次计划批准。
- 每项授权必须保存到 `.ai/<task-id>/grant.md`，并至少记录日期、权限、原因、是否同意、授权人（`user` 或 `ai`）和申请人（流程环节）。
- 计划之外的危险动作、目标/范围变化、冲突或无法安全判断，仍不得沿用旧授权，必须重新取得适用授权记录。

### Git 交付边界

- 获授权的具体交付计划只可包含本地 `commit`、创建分支和本地 `merge`。
- `git push` 和任何直接 Git 删除绝对禁止；不得以重试、清理或其他交付步骤绕过。
- worktree/branch cleanup 只能经 AIW 生命周期操作，不能通过原始 Git 命令执行，并须受对应 grant 记录约束。

### 通知协议与重试

- 通知只发送文本内容，并通过 `aiw-notify` 插件实现；首期至少支持 `console` 与 Microsoft Teams，Teams adapter 调用 `send_teams_msg.py`。
- 不假设接收方存在查询、可靠幂等或送达回执接口。通知只能记录“已尝试”或“失败”，绝不记录“已送达”。
- 仅当插件明确报告网络失败时，等待 1 分钟后自动重发 1 次；任何其他失败、未知结果或已完成的重发均不自动重发。
- 由于没有可靠幂等或回执，网络失败后的这一次重发可能导致重复投递；这是已确认的产品策略，记录必须保留两次尝试的因果关系。
- 严格通知模式及旧独立调用的兼容实现改由 `aiw-notify` 插件边界处理；adapter 的凭据、传输安全和参数细节仍须在工程设计中明确。

## 关键业务规则与例外

- 接受须同时具备有效报告、当前适用的受控编译/单元测试证据；Coder completed、Session 成功、waived 或清单勾选不能绕过。
- 相关实现、测试/fixture、配置/依赖、计划、需求验收或范围变化会使旧通过证据失效；日志、时间戳或 memory 更新本身不会。
- 结果未知时先核实；只有可证明未派发或安全重发才重发。重启、换 Session、修改配置或 resume 不得重置 Stop、授权、预算、失败或恢复计数。
- 自动测试只限 AI 授权的计划和安全范围。删除、项目外路径变更、链接目标不明或副作用不明须请求新的适用授权；无法判定则停止受影响动作。
- 外部通知不以本地成功冒充送达；除已确认的“明确网络失败后一分钟重发一次”外，不自动重发。凭据不得进入参数、日志、消息或工件。
- Verifier 只读并固定其审阅输入版本；报告记录成功不建立 Gate、不撤销接受/完成，也不自动触发返工。
- Git 交付只可在实际计划、分支/父分支、范围和允许动作已显示并由 AI 批准后推进；禁止 push 与直接删除，cleanup 仅通过 AIW 生命周期及 grant 记录进行。

## 来源中的方向性决定与依赖

- **D21（来源记录）**：本批拟采用一个整体 Requirement、一个 Task/change 生命周期，内部使用 E01–E08 分组；这不是当前 Task 创建或推广授权。
- **D22（经用户确认修订）**：通知由 `aiw-notify` 处理，至少支持 console 和 Microsoft Teams 文本发送；接收方无查询/送达回执假设，兼容边界由插件处理。凭据、传输安全和 adapter 参数仍须工程设计。
- **D23（经用户确认修订）**：具体 Git 计划由 AI 批准并写入 grant；只允许本地 commit、创建分支和本地 merge，禁止 push 和直接删除；cleanup 仅经 AIW 生命周期操作。
- **E01–E08（候选工程分组）**：执行事实/基础上下文、阶段恢复/写入权、测试闭环、路由预算、Task memory/后台宿主、知识治理、通知、独立 Verifier。它们是后续工程规划输入，不冻结 API、并发或持久化 schema。

## 假设

- `aiw-notify` 将被扩展为 console 与 Microsoft Teams 文本 adapter；它不提供查询、可靠幂等或送达回执。
- 除上述政策决定外，没有新增已确认业务假设。可恢复的旧 Session 未保存事实及收件人可访问本机路径均不得假定存在。

## 待决问题与需要的后续决定

1. **通知 adapter 设计**：`send_teams_msg.py` 的配置、凭据引用、传输安全、网络失败分类和错误契约尚待工程设计；重试策略已确定。
2. **grant 与 AIW 生命周期集成**：`.ai/<task-id>/grant.md` 的原子写入、校验、读取、AIW cleanup 操作与迁移/恢复方式尚待设计；字段和授权政策已确定。
3. **工程设计闭合**：状态机、存储、索引、并发、恢复信号、参数上限和 E01–E08 依赖须在推广后工程设计中完成；未闭合部分不得实施。
4. **整体正文审阅与批准**：当前仅捕获草案。SW/AC/AX 的完整语义和批准时机仍需此 Requirement 的人类审阅；产品中的 AI 授权机制不替代该 Requirement 的受管批准检查点。

## 拟延后至工程设计的事项

这些事项是候选工程细化，不是对任何业务规则的豁免：D16-E 所述 token/批量/存储参数、持久化结构与索引、并发控制、恢复信号、`grant.md` 的原子记录和校验、AIW cleanup 集成、通知 adapter 的凭据/传输安全/错误分类，以及 E01–E08 的具体接口和迁移设计。原因是来源明确要求在对应能力实施前设计并记录，且当前没有批准为实施计划。

Requirement 已具备来源追踪、候选范围及三项已确认政策决定的草案，但尚无整体内容批准，也不具备 Design Readiness 或推广条件。下一受管动作应是人类审阅本 Plan 并在另一个检查点决定是否批准；批准后才可单独决定是否推广为 Task/change。

## Confirmed Workflow

本节仅将已批准范围按工程交接 E01–E08 整理为 AIW 推广所需的编号清单，不新增需求或实施授权。各组须先闭合对应工程设计，再实施和取得验收证据；临时来源与本 Plan 政策修订冲突时，以已确认的修订为准。

1. E01 执行事实与基础上下文：保存每轮报告、绑定身份、验证输入与来源版本，处理失效和旧 Task 复用；追踪 SW01–SW04/SW25、AC01–AC04/AC25。
2. E02 阶段、恢复与写入权：建立阶段转换、串行写入权、未知结果对账、Stop 和可恢复预算；与 E03 共设接受边界，追踪 SW05–SW08/SW14/SW33、AC05–AC08/AC14/AC33；Git 本地交付由 AI 审批，仅允许 commit、分支创建和本地 merge，禁止 push 和直接 Git 删除，cleanup 仅经 AIW。
3. E03 独立 Tester 与测试闭环：以需求构造测试，按 AI 批准的计划执行、判定风险并回交修复，凭当前证据接受；授权记录使用 .ai/<task-id>/grant.md 及已确认字段，追踪 SW10–SW14、AC10–AC14、AX01/AX03。
4. E04 模型路由与预算：按生成请求去重归因，实现每档两次有效失败、每 Actor 最多两次升级和共享六次修复上限，保留跨重启预算；追踪 SW08/SW15–SW17、AC08/AC15–AC17。
5. E05 辅助宿主与 Task memory：持久登记有界后台工作，保存固定输入及一次恢复账、Task 来源和 Session 投影，处理 Stop、重启和迟到结果；追踪 SW09/SW18/SW19/SW24/SW25/SW27、AC09/AC18/AC19/AC24/AC25/AC27。
6. E06 知识生成、审阅与注入：实现异步提取、部分覆盖、版本化五态审阅、读取时复核、确定性选择及历史处理限额；追踪 SW20–SW27、AC20–AC27、AX05。
7. E07 文本通知：通过 aiw-notify 支持 console 与调用 send_teams_msg.py 的 Microsoft Teams 方式；仅记录已尝试/失败，明确网络失败后等待 1 分钟（60 秒）后最多重发一次，其他情况不自动重发；追踪经政策修订的 SW28–SW30、AC28–AC30、AX04。
8. E08 独立 Verifier：固定需求、diff 和验证证据版本，异步只读审查并记录 failed/inconclusive/passed，不阻塞接受、交付或 Task 完成；追踪 SW19/SW27/SW31/SW32、AC19/AC27/AC31/AC32。
