# 自动化开发 Workflow：统一软件需求正文

版本：临时整合稿 v2，2026-09-16；已同步 D21/D22/D23。不是正式 Requirement Plan 批准记录、OpenSpec spec 或实施授权。

## 1. 来源、事实与确认边界

- 原始目标：[tmp-issue.md](../tmp-issue.md) §1～§8 及 Verifier 附节；目标是自动化开发，减少不必要的人工介入。
- 行为依据：[decisions.md](decisions.md) 中 54 项局部决定及 [R01～R10 分析入口](README.md)。决定只确认对应范围，不自动批准本整合稿的新表述、工程方案或验收结果。
- 现状依据：[稳定规格索引](../../openspec/specs/README.md)，基线日期 2026-09-16；实际目录为 `openspec/specs/`。它是源码行为基线，不是全部能力已通过测试的证明。
- 实现差距沿用 [既有静态取证](review-gap-plan.md)，本轮补核稳定 spec，未重新检查所有生产代码。规格、代码与目标的对应关系见 [工程交接](engineering-handoff.md)。
- [验收追踪](acceptance-traceability.md) 将本文 SW 编号连接到来源、决定、工程分组和待取得证据。SW/AC/E 均为临时追踪编号，正式化时保留映射，不冒充 AIW ID。

已核实的现状：supervise 接通 Coder 与编译；Tester、Verifier 和通知的基础类型/辅助接口不等于完整自动流水线。当前完成、重试、授权和模型快照行为与目标存在明确差异。

假设与限制：本稿不假设外部通知服务具有可靠幂等、查询或送达回执；不假设可恢复旧 Session 中未保存的事实；不假设本机路径可被收件人访问。D21 已确认一个整体生命周期内按 E01～E08 分组，具体设计及实施计划尚未批准。没有新增已确认业务假设。

## 2. 使用者、职责与目标

项目操作者/已指定负责人负责必要的需求、授权及知识审阅决定。Supervisor 按可解释规则编排和保存事实；Coder 实现，Tester 独立设计和修复测试，Compiler/Test Runner 产生真实执行证据。Context Builder 组织输入，Model Router 选择已配置模型。memory、知识提取/汇总与 Verifier 是辅助工作，不能代替开发接受规则。

Task 是整体工作生命周期；Work Item 是可接受的实现项；Attempt、阶段请求、Session 和 turn 是不同执行身份，不能互相冒充。接受是当前报告和适用验证条件成立；Task 完成、Git 交付、知识确认、Verifier 结论和通知送达是不同事实。

目标是实现可恢复的 Coder—编译—Tester—测试—接受闭环，形成可追溯证据、跨 Session 上下文和可审阅知识；在授权范围及预算内自动推进，只在缺少必要决定、危险/未知操作或无法安全恢复时请求人工。

## 3. 范围与非目标

范围覆盖 R01～R10：报告、阶段、单元测试、路由、Task memory、项目知识生成及审阅、角色上下文、通知、只读 Verifier，并覆盖所有未完成 Task 的兼容恢复。

不包含集成/E2E 或第三方业务接口测试、自动语义向量检索、全项目无差别历史补处理、自动批准知识或需求、Verifier 自动返工、永久后台服务或开机自启。通知传输属于本范围，但不因此扩大开发测试的网络权限。

本稿不授权执行测试、网络请求、Git 提交/合并/清理、生命周期创建或配置变更；也不修改现行 stable spec。产品拟实现的自动化政策与本次文档工作的执行权限分开。

## 4. 功能要求

以下“必须/不得”表达拟交付的目标，不表示已实现。每条验收入口为同号 AC 条目。

### 报告、证据与兼容（R01）

- **SW01 每轮报告。** 每次实现/修复结果必须保存可追溯报告，绑定实际 Task、Work Item、Attempt、角色和 turn；包含需求覆盖、变更位置/版本、可观察输入输出及副作用、测试入口、决定/限制/风险、验证引用和历史关系。确实为空、未知与未验证必须区分；不为报告强造公共接口，不覆盖旧报告。
- **SW02 报告校验与补交。** Supervisor 确定性核对报告内容、执行绑定和引用。缺失或无效时最多追加一次仅报告补交，关联原执行及补交身份，不重新派发源码修改；仍失败转人工。不得以模型升级、重启或新 Attempt 刷新补交额度。
- **SW03 证据有效性。** 编译与测试通过只能来自受控执行记录，不能来自 Agent 声明。当前接受须证明实现、测试/fixture、相关配置/依赖、计划、需求验收及适用范围一致；发生相关变化则旧通过证据失效。报告、日志、时间戳、memory 更新本身不使证据失效；不能仅凭 HEAD 或 Git 状态字母相同判定内容相同。
- **SW04 旧 Task 与下游读取。** 所有未完成 Task 采用新接受规则：适用且可核实的旧结果直接复用；仅缺报告按 SW02；缺有效证据按当前授权重新验证，缺授权则暂停相关执行。不可恢复理由标未知，不补造事实或强迫重写已有效代码。Tester 可读待接受的实现报告；依赖 Work Item 只能使用已接受且仍适用的成果。

### 编排与恢复（R02）

- **SW05 阶段及写入权。** 每阶段明确进入条件、执行者、输入版本、输出接受条件和失败去向；请求冻结身份、角色、模型、范围及输入。Coder、Tester 串行持有写入权，只有 Supervisor 在持久终态或安全恢复后转交；Coder completed 仅结束实现阶段，不结束整个 Attempt/Work Item。查询须显示阶段、在途身份、阻塞原因、证据和剩余预算。
- **SW06 未知结果与 Stop。** 结果未知先核实；仅能证明未派发或可安全重发才重发。缺报告、超时或前台退出不能证明执行结束，不得重复双写或擅自释放租约。明确 Stop 阻止新派发，重启不解除；在途执行需对账，不能伪称已停止、已撤回或安全清理。
- **SW07 故障分类与恢复。** 规则先识别实现/测试缺陷、基础设施、需求未决及缺报告；缺陷归属不清时，排除明确环境/需求问题后最多一次独立只读诊断，无效或仍不清转人工。基础设施故障同 Work Item 同阶段最多追加 2 次恢复，须无执行器在途、可安全重跑且条件满足；缺条件等待。无进展按实际原因归类，不另加预算；耗尽只暂停受影响执行。
- **SW08 预算恢复。** 失败、升级、修复、恢复和已用授权事实必须可恢复，重启、换 Session、配置/环境恢复或普通 resume 不刷新。旧计数先自动重建；证明余额足够可继续，不能证明时不归零或伪记耗尽，按 Task 集中请人工决定后续额度，有效旧结果仍可复用。
- **SW09 有界后台工作。** 随任务启动的有界后台执行器继续处理已登记且获授权的辅助工作，队列处理完退出；前台结束和 Task 完成不丢弃工作。遵守 Stop、范围、各自预算和在途对账；首期无永久服务/开机自启要求，关机不承诺执行，下次启动先恢复事实。

### 单元测试与接受（R03）

- **SW10 独立 Tester。** 编译通过后，Tester 在独立上下文中取得原始需求/验收、实现报告、接口清单、源码、已有测试/fixture 及范围约束，产出单元测试、用例清单和执行计划。预期行为以需求为准，不按当前实现反推断言；写入限获准测试路径，不与 Coder 并写。
- **SW11 具体计划与自动发现。** 初始具体测试计划须人工批准；默认明确限定模块/路径、发现选择规则、执行约束及资源上限。授权范围内新增或修改测试/fixture 自动执行，使用新证据，不逐用例重批。显式固定选择的旧计划仍按其授权处理；其他实质计划变化重新授权。执行前检查实际范围/副作用，保留宿主权限、受控命令和无网络等约束。
- **SW12 权限危险性与 LOG。** 权限请求先由 Supervisor 按可解释规则审查实际操作、路径/链接目标和副作用，模型不能自行放行。删除、修改项目外文件等为危险，构成新计划须重新人工授权；无法判断转人工。明确不危险，可靠记录 LOG 后继续而不重批。LOG 失败先对账，再用所属阶段 SW07 原额度恢复，复用仍适用的审查、不另调模型；仍失败暂停依赖该记录的动作。相关操作/内容/目标/规则变化自动重审，不等于自动转人工。
- **SW13 修复闭环。** 受控执行器保存退出码、超时、输出、计划与输入版本；缺陷回交责任 Coder 或 Tester，环境问题不靠改代码或升级解决，需求冲突转人工。Coder 不得删弱测试消除失败；Tester 修改须有依据并保留历史。修复后重新编译和相关测试，接口变化须检查用例适用性，次数遵守 SW16/SW17。
- **SW14 接受与不适用。** 有效报告、当前适用编译和单元测试证据满足后才接受并释放下游；清单勾选、Session 成功或 Coder completed 均不能绕过。明确不影响可执行行为的变更可按规则记录单元测试不适用，疑问转人工；执行型 prompt/配置/脚本不按纯文档处理。不适用、未执行、waived 与 passed 分开，旧可选测试 waived 不能替代新的必需测试。

### 模型与预算（R04）

- **SW15 路由。** 固定配置的路由模型结合 Work Item、角色、需求、上下文和失败选择已配置 Profile，记录理由；失败或无效推荐使用配置默认档位，不递归路由或逐次人工选择。Compiler/Test Runner 不选模型；名称不代表能力，相同实际 provider/model 的别名不算升级，历史请求快照不可回写。
- **SW16 角色失败与升级。** 接受前按 Work Item、责任 Actor、当前模型档位累计有效失败；同一生成执行的多条缺陷/重复读取不重复计数，延迟发现归到生成该产物的请求。中间成功、其他角色活动、环境故障均不清零。每档两次有效失败后，在确需且允许派发时升级到下一不同模型，每 Actor 最多两次；无更高模型或耗尽且达到失败阈值则暂停。新档从零、历史保留，Work Item 接受后结束计数。
- **SW17 修复上限与优先级。** 测试失败回交后的修复派发由 Coder/Tester 共享最多 6 次；第 6 次结果满足条件仍接受，不允许第 7 次自动修复。已归因实现/测试缺陷以新规则替换旧三次连续编译失败及同类普通重试；报告/诊断/辅助/通知各自更小或专门上限优先，不叠加基础设施额度。先判断已有结果是否成功，再判断是否允许下一次派发，不虚扣未发生的升级。

### 任务记忆与辅助恢复（R05）

- **SW18 Task memory。** 原始报告、决定和阶段事实跟随 Task，Session memory 只是投影。已接受成果与进行中/失败内容分区；摘要不能代替授权、计数或人工决定。实质成果/决定/待办/风险变化才刷新，派发前核对来源，新 Session 从 Task 重建；迟到旧摘要不得覆盖新视图。摘要不可用不撤销接受/完成，必需原始工件完整可降级，否则仅暂停受影响派发；不得覆盖人工原文。
- **SW19 辅助恢复统一边界。** memory、知识提取、知识汇总和 Verifier 各对固定输入最多追加一次恢复，不自动升级。确定终止无可复用结果重调、无效输出重生成、有效结果重存共用原额度；未知先核实，不通过重启/新 Task 引用相同历史输入刷新额度。耗尽标不可用，不重开实现/测试或阻塞其他安全工作。此规则不适用于通知、报告补交、诊断或 Coder/Tester 修复。

### 知识生成及治理（R06/R07）

- **SW20 提取与汇总。** Work Item 接受时登记异步提取，Task 完成事实保存后异步汇总且不等待。记录可复用规则/决定/经验、来源和证据性质，允许有依据的“无新增”；未成功提取不能记无新增。只从已有失败证据提取观察，不因每次失败新增提取循环。失败状态与开发完成分开。
- **SW21 部分覆盖及版本。** 汇总列明应覆盖的 Work Item、成功/运行中/失败/缺失状态及条目来源；可发布带明确缺口的部分草稿。补齐或来源实质变化生成新版本，不覆盖人工编辑/审阅、不继承新正文的旧确认；不变条目保留本版本确认，不因整份汇总升级而全量重批。
- **SW22 知识五态与审阅。** 以条目版本为审阅单位，支持候选、已确认、待复核、已拒绝、已废弃；部分条目可确认。操作条件绑定所见版本，版本冲突不得静默覆盖。人工编辑产生新候选，可明确确认新版本；记录主体/时间/来源和历史。仅人工确认/拒绝/废弃或建立替代关系；废弃不以已有替代为前提，重复输入不得绕过拒绝。
- **SW23 失效及复核。** 关联变化异步标待复核，读取时再核对，不能检测时明确说明，不自动判错/废弃。正文、关联来源及范围未变可在原版本追加人工复核；正文、绑定来源版本、证据性质、范围、使用方式或失效条件实质变化生成新候选，即使结论文字相同也不继承确认。无关文件、显示顺序、时间戳变化不升级版本。只有人工复核可恢复主参考。
- **SW24 人工介入及文档边界。** 优先已指定负责人，否则当前项目操作者；身份未验证明确标注，不授额外权限。旧 Session 唯一人工文本保留原文/来源导入候选，可关联可核实正式决定则直接引用；不确定且影响执行时集中询问。普通知识审阅进待办而不阻塞开发；仅无法安全满足当前需求/验收/授权时请求裁决。知识确认不自动同步 CONTEXT、ADR、需求、代码等，首期只记录建议同步及来源。

### 上下文与资源（R08）

- **SW25 实际输入与缺口。** 每轮提供需求、任务上下文、handoff 和相关知识的实际内容，按角色组织；保存实际 prompt、来源身份/版本/状态、读取错误、选择/跳过和降级理由。核心主来源、角色边界、必需依赖缺失或版本无法解释则阻塞受影响派发；完整原始工件可替代不可用摘要。普通项目知识可选，读取失败不冒充零命中；只有被已确认主来源精确纳入的知识版本成为必需约束，handoff 不自行加约束。历史输入不被 latest 回写。
- **SW26 知识选择与冲突。** 首期按模块/路径/接口/领域标签和少量通用规则可复现地选择，可信状态分区。已确认且适用可作主参考；候选/待复核带警示作次要参考，不能单独驱动实现或验收；拒绝/废弃不自动注入。主来源优先，普通知识冲突只降级/记录；无法安全满足主来源、兼容或授权边界才转人工，不因偏好分歧阻塞。
- **SW27 资源及历史范围。** 必需输入优先不可截断；可选知识超预算按确定顺序跳过并记录。当前需要时自动回填相关模块/接口/依赖的历史知识并作只读补审，先复用已有结果；单批及当前 Task 累计硬上限，拆批/重启不刷新，超限不自动扩额，可选工作停止、其他安全开发继续。首期不按保留期自动删除证据，空间不足暂停受影响写入并提示。具体 token/批量/存储参数由工程设计在对应能力实施前确定并记录，这是 D16-E 唯一明确获准的参数后续细化分工。

### 通知（R09）

- **SW28 事件与内容。** Task 完成事实保存后立即生成通知，不等 Git/知识/Verifier；需要人工处理的有效阻塞产生可行动提醒，普通进度静默。同一事实不重复通知，重要晚到结果关联更新；分别显示开发完成、交付、部分草稿/缺口、审查状态，不以辅助失败新建开发阻塞。不把本地接收或零退出码宣称外部送达。
- **SW29 发送与恢复。** 每通知内容版本含首次最多发送 3 次，两次默认等待 30 秒/2 分钟；缺配置先等待不调用，实际发送失败保留次数，重启不清零。送达未知先核实，仅可靠外部幂等仍有效时同目标/正文/键有限重试，否则不自动重发。主动禁用后再启用只自动补当前有效未送达的人工提醒，不全量补历史完成；保持启用期间的故障消息条件恢复后续发。过期阻塞取消未派发提醒，在途不伪称撤回；时间戳/重渲染不刷新版本或预算。
- **SW30 配置与外发边界。** 使用项目级配置和显式解析参数，脚本按项目根定位；不得由脚本隐式默认值改投目标或凭据来源。凭据只按约定的环境引用取得，不进入消息/日志/工件；输出最小脱敏摘要和授权范围引用，不自动上传源码或日志，不虚构可访问链接。目标冻结于通知版本，配置变化不静默改投旧消息。现有 CLI 优先级、adapter 参数及外部回执协议须按交接 H02 核实；本文不虚构该契约已确定。

  D22 补充：新增受管严格模式，参数显式传入，不加载隐式 `.env`/配置、不回退默认目标；凭据不得进入命令参数或日志。验证服务证书，需要时配置可信 CA，不沿用旧脚本跳过证书校验的行为。独立脚本旧调用保持兼容。外部回执/查询/幂等由工程取得协议依据，未证实前按 D18 保守处理。

### 独立审查（R10）

- **SW31 独立输入与执行。** 接受时固定并登记独立需求/验收、实际 diff、实现及编译/测试证据版本，之后异步实际派发只读 Verifier；不只保存类型或以 Coder 报告替代独立输入。报告写入受管工件，不获得源码修复职责；下游和 Task 完成不等待，晚到报告只适用于被审版本。历史补审不重开实现或执行测试，遵守 SW19/SW27。
- **SW32 审查结论与隔离。** 按验收项保存依据和缺口：有依据的不满足为 failed，无明确失败但证据缺口为 inconclusive，全部适用项有充分依据且通过才为 passed；无报告、空覆盖及执行故障单独显示，不凑 passed。合法负面结论不是模型调用失败。报告成功保存只表示记录成功，不创建 Gate、不撤销接受/完成、不触发返工或阻断 Git delivery。

## 5. 横向质量约束

- **SW33 Git 具体交付授权。** 按 D23，在实际执行前一次展示并批准具体 Task 交付计划，明确 Task 分支、父分支、可提交范围和清理目标，提前明确包含危险删除。只有同计划、授权有效且状态可证明安全时才自动推进，不逐步重批。新增危险动作、目标/范围变化、冲突或无法判断时停止相关交付并重新请求决定；结果未知先对账，不盲重放。不得提交无关改动，清理前保全后台工作所需来源；push、PR、archive 不在该授权内。本条不是对当前仓库任何实际 Git 操作的授权。
- **SW34 生命周期及设计闭合。** 按 D21，本批采用一个整体 Requirement、一个 Task/change，内部按 E01～E08 分组实施。正式推广前明确目标、验收及授权边界；推广后由工程规划补齐状态机、存储、迁移、恢复等设计，对应设计未闭合不实施该部分。不逐字段请用户确认，改变已确认行为、授权或成本边界才重新提问；不得将未决业务规则作为工程延期豁免。正式创建、捕获、批准、推广仍须各自受管检查点。

自动化必须有界、可解释、可恢复；原始事实、输入快照、授权和计次不可被派生摘要替代。局部失败只影响真正依赖它的动作；资源不足或资料缺口不能通过删除证据、降低必需输入或扩大权限掩盖。

持久化格式、索引、并发控制、恢复信号和协议参数尚非冻结设计；实现必须先形成对应设计并证明满足上述可观察行为。不能以“未来设计”豁免业务缺口，也不能因 U01～U08 已收敛宣称整体 plan_review 通过。
