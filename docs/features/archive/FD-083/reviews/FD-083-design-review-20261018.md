## 同次审阅收尾核对

已只读核对 FD 新增的“独立设计审阅后的边界补充”，未开启新一轮或扩大范围：

- D1 已解决：候选 latest 与精确依赖冲突直接失败；最终状态包括未更新包和反向依赖；默认集合仅保留原有且新版仍声明的成员，成员版本不符同样拒绝。
- D2 已解决：S3 持锁重读、包先索引后、unpublish 索引先对象后；失败清理限于本次未索引新对象，响应不确定时报告未完成状态；不自动接管锁。实现必须保持不确定提交时不盲删可能已索引对象。
- D3 已解决：首次变更前准备下载、图、配置与模块；官方 pkg 无 hook；执行中不重新导入更新模块或启动解释器读取它们；Windows 退出 EXE 后经独立 Python 入口更新。

## 发现

### D1（高）：精确依赖与默认 latest 更新缺少一致的最终图规则

位置：FD 的“包与安装”DFS、current.json 与默认 update 条款；Work Item 1.5。

FD 同时规定精确 name/version 依赖、默认更新已安装内容的 latest、集合不补装新成员，但未规定这些规则冲突时的行为，也未明确将本轮不更新的已安装包纳入反向依赖校验。

例：已安装 A@1 依赖 B@1；仓库只有 A@1、B@1、B@2。默认 update 若把 B 更新成 latest B@2，A 的精确运行依赖立即失效。`update --core` 也可能替换被范围外 extension 精确依赖的 core 包。只有对本轮下载包做 DFS 不能排除这种错误。

建议在 FD 固定：先构造候选最终安装图，包括所有保留的已安装包；所有保留的精确依赖必须能由同名同版本节点满足，禁止同名多版本。候选 latest 发生冲突则在首次写入前拒绝整轮并显示引用链，不隐式降级或更新范围外包。集合记录区分“发布清单”和“实际保留成员边”，默认更新可只记录实际安装子集；对仍保留的成员边也要确定版本与最终节点一致的规则。补充上述普通包和范围外依赖两个验收例。

### D2（高）：S3 写入只有加锁意图，缺少与 filesystem 相同的提交和失败契约

位置：FD 的“Repo 与协议”S3 条款；Work Item 1.3。

local 已明确持锁重读、不可覆盖、先包后索引与删除清理顺序；S3 仅声明条件建锁和重读索引。S3 adapter 不复用 filesystem 的原子替换，不能据此推定其发布顺序及失败行为。包上传成功、索引提交失败，以及索引删除成功、包删除失败都需要可判定结果；中断遗留锁也需要明确恢复提示。

建议明确 S3 与 local 使用同一逻辑写入契约：独占锁覆盖读取、验证、包提交和索引提交；publish 在验证暂存内容及不可变身份后先写规范包对象，再一次提交新索引；只有尚未被成功提交索引引用的新包允许失败清理，既有包不可删。unpublish 先提交移除条目的索引再清理对象，失败须报告真实可见状态。锁写入唯一操作标识，仅由持有者释放，异常保留锁时报告锁位置及人工排查方式，不自动夺锁。若工具不支持所需条件写入，明确失败，不退化为无锁写入。

### D3（中）：pkg 自更新的“预先导入”没有覆盖运行中后续源码依赖

位置：FD 最后一条“命令与构建”；Work Items 1.5、1.7、1.8。

现有 aiw-pkg.py 在启动时导入 archive/manager，因此单纯保持这两个导入不代表新增 Repo、resolver、Skill 模块和脚本也已冻结。manager.py 的 hook 会创建 Python 子进程；如果更新过程中再执行已替换模块、脚本或依赖旧运行时的 hook，独立 Python 入口本身仍可能混用新旧代码。

建议固定一个实现边界：开始安装图执行前加载本次操作需要的所有引擎模块和资源，操作期间禁止按安装根再次动态导入引擎；下载包及其 hook 保存在独立暂存目录，hook 不依赖正在替换的安装器源码。提供依赖先于引用者的确定性安装顺序，并明确 pkg 自身更新不重启当前解释器；Windows 由 aiw 主进程占用的 aiw.exe 仍按已确认的失败提示和独立入口重试处理。无需引入后台更新器或整组回滚。

## 范围与可行性

- Issue 的本地/HTTP/S3/SSH、集合、独立小包、Skill 作用域、卸载、core/all、唯一归属和离线构建均已有 Work Item 承接。v2 集合单独建模是必要的：现有 archive.validate 严格要求 format_version=1、非空 files 和固定 kind。
- 共享资源由唯一 resource 包持有、Skill 显式依赖资源，是可行的方向。应在发行元数据中具体列出资源包名和主程序/Skill 的精确依赖，避免把“主程序随带根 Markdown”实现为重复文件归属。
- 独立打包可在现有 package_component/tree_entries/write_package 之上拆分；现有 docs、plugin-tools 聚合分支不能直接保留为新的独立发布单元。新增 scripts 入口应由 build.py 显式调用共同打包库，发行清单固定成员，不能在安装时扫描源码。
- SSH 复用远端 filesystem 引擎方向合理。需把远端脚本位置、命令参数和兼容版本写成清楚的部署前提；远端缺少脚本时失败，不自动安装。上传暂存、远端校验、持锁提交的顺序应沿用 local 契约。
- 现有 manager.restore 会写回每个已存在快照文件；Windows 未改动但被占用文件也可能导致恢复失败。Issue 已接受沿用事务并如实报告失败，因此不要求增加占用检测或恢复算法重构，验收与最终报告不得声称必然完整恢复。
- 1.3、1.5、1.6、1.7 都跨多个契约，目前“小/中、半天以内”只是估计。实施前宜按本报告的边界追加稳定子项，将 adapter 写入、最终图规划、Skill 迁移、发行资源归属拆开提交。
