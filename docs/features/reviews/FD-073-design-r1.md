## D1：独立 FD 映射与冲突阻断规则冲突

FD 同时要求“所有 Issue/FD 映射目标不一致则阻断”和“用户明确要求分开跟踪时允许独立 FD 映射”。独立映射建立后，下一次发布会遇到父 Issue 和 FD 的不同目标；当前设计没有说明如何识别已授权的分开跟踪，容易永久阻断，或者由模型临时忽略映射冲突。

建议：明确持久化的关联策略（例如独立 FD 映射可选字段 `relationship: independent` 及关联 Issue 身份），或要求每次显式选择独立目标并核验已有授权。默认仍检查双方映射；只有明确独立策略才允许两个目标并存。另明确关联 FD 首次发布且父 Issue 尚无映射时，创建结果写入父 Issue 的所有权映射，`source_kind/source_id` 标识映射所有者，FD 受管块身份单独计算，不能混用。

验收例：Issue-A 映射远程 #10、已授权独立 FD-B 映射 #11，重新发布 FD-B 更新 #11；没有独立策略的同样数据必须阻断。首次从普通关联 FD-C 发布时创建一个远程 Issue，保存 Issue-A 所有权映射，随后发布 FD-D 复用该目标。

## D2：未知 create 结果需要可恢复的本地证据

“未知结果先核查、不重试 create”是正确规则，但只要求保留响应或目标，未覆盖请求超时且没有响应、或远程成功后进程退出的情形。此时映射缺失，下个会话按“没有映射则 create”仍可能重复创建。

建议：在远程 create 之前持久保存一个最小发布意图/恢复文件，记录来源所有者、仓库、投影身份/内容摘要和结果未知状态；意图保存失败就不发送请求。请求成功后保存已知响应/远程身份，再原子提交正式映射。任何未完成意图都阻止新的 create，恢复只允许读取 GitHub 核查并修复映射；无法唯一识别时保留现场、报告阻断。该记录可由 Skill 通过现有本地文件方法处理，无需引入自动同步引擎或新产品 CLI。

验收例：create 已发出但无响应，新的会话看到未完成意图就停止创建；已知远程号但映射保存失败时，只恢复该号的映射，不重新发布。

## 实现注意事项

- 来源 ID 使用记录的 canonical identity，不能将用户缩写或可移动的归档路径作为身份；文件路径拒绝路径穿越，大小写规范一致。
- 新来源替换应保留块外原始字节；旧两参数接口的历史空白处理可保持兼容，不应对旧接口许诺原本没有的字节级行为。
- 远程 Issue body 是整体验证后回写；纯 helper 无法提供远程并发原子性。文档应说明单次写入前重新获取最新 body、避免并行发布，并如实说明缺少条件更新时仍有竞争窗口，不能宣称绝对保护并发人工修改。
- 现有 `version=1` 映射兼容应指有效旧格式，不能继续接受 Python 的布尔型 Issue 号、非正整数或与仓库/编号不符的 URL。
