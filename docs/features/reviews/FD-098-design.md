## 静态评估

- `Operation.install` 在遍历前选择所有根；默认 update 的根已覆盖所有旧安装包。因此仅在默认 update 的 member 边指向已选根时省略 wanted，能使用成员的最新选取，嵌套集合亦同。dependency 边必须保持 wanted，即使目标也是更新根，也不能覆盖真实依赖冲突。
- 显式 install 集合和带 scope 的 update 保留精确 member 选取。显式多个根之间的版本冲突仍应失败；默认更新的放宽条件不得扩展到这些入口。
- preflight 的 final 图含未选中的已安装节点，正是旧集合记录阻止独立升级的位置。拆开两类边后，dependency 检查存在且版本相同，member 检查存在，两者继续递归并使用同一 active/visited 检测循环，能保留缺失成员和反向真实依赖保护。
- `Manager.record` 仍可解析旧 name/version 引用；`remove` 和 `orphans` 已按名称处理关系，不需要放宽记录校验或调整删除逻辑。单成员升级无需选择或重写旧集合记录，历史 member.version 不能冒充当前成员版本。
- 默认 update 的既有成员交集裁剪应保留，避免补装集合新成员。更新集合元数据时可以沿用当前声明/裁剪流程；“无需迁移旧记录”不应理解为禁止正常更新集合元数据。
- 锁下快照复核、完整规划后 preflight、dry-run 跳过写入、逐包事务与部分失败边界均可原样保留。此设计不承诺整批原子性，也不授权安装或发布。

## 实现与规范注意点

没有阻止设计进入实现的发现。实现时应同步稳定规范中“集合、依赖和安装原因”“共享本地安装规划”及 no-op 更新规则里笼统的精确版本措辞，明确精确配方选取与持续运行依赖检查的区别。使用文档应说明集合自身版本不会随成员单独升级而改变，成员实际版本以自身记录为准。

本机旧技能仍可能通过真实 dependencies 阻挡共享资源升级，这属于本 FD 明确排除的兼容版本问题。完成集合修复不能表述为主程序已经安装成功或全部依赖冲突已经解决。
