## 判断依据

设计覆盖 ISSUE-00009 的成功后清理、失败保留、外部输入不删除、只处理当前源以及失败警告要求。正式工件和 `Write(meta)` 成功后才进入清理，清理错误通过本次返回值携带，不回滚正式结果，兼容现有 capture 成功退出语义。

当前 `Capture` 使用 `os.ReadFile`，本身没有文件身份或删除保护；FD 没有误将上下文读取的保护视为已有删除授权。拟新增 helper 应同时负责受限资格、读取快照和保存后的清理，避免两个调用点分别实现安全规则。

以项目词法路径匹配两个明确草稿根，拒绝原始上级分量、ADS、根以下链接和非普通文件，同时容许受管理的 `.ai` 共享存储，能够兼顾 worktree 与删除边界。`os.Root` 用于限制访问，额外拒绝根以下链接仍然必要；它不能单独表达全部业务规则。根身份变化时保留并警告是必要的降级。

初始 `FileInfo`、打开后 `SameFile`、实际 capture 字节绑定，再在随机私有目录内核对隔离对象，可避免仅凭路径或相同内容误删替换文件。隔离后不匹配时无覆盖恢复，恢复失败保留隔离文件和可定位路径，优于覆盖新源或递归清理。此方案不构成跨进程锁，FD 已明确边界；不能据此宣称消除了任意并发写入窗口。

相对直接删除，隔离与恢复增加了复杂度，但它服务于明确的源替换保护和无覆盖恢复要求，有采用依据。建议把该流程集中在一个 helper，使用现有标准库能力，不扩展为平台专用并发锁或后台机制；无需为最后一次核对后同用户恶意篡改增加锁协议。

`Artifact` 的现有 TOML 写入逐字段生成，批准摘要使用 JSON 编码工件 map；新增字段使用 `json:"-"` 并保持现有字段不变，可保留既有摘要结构。清理警告只需放在返回给调用方的 Artifact，不应再持久化为工件状态。

两个调用点均在 capture 成功后消费警告，并在聊天后续摘要核对或事实保存之前打印，能够保留现有事实确认语义。聊天后续失败不恢复已消费草稿，与 Issue 将正式工件及元数据作为保存成功边界一致。

## 实现时必须落实的已有约束

1. 保存快照时固定实际文件身份，不能在第二次打开后用新身份覆盖旧身份；隔离后的核对需包括内容与属性变化。
2. 清理始终使用固定草稿根句柄，重新核对可见根与初始身份；不能以任意 `EvalSymlinks` 结果扩大清理资格。
3. 隔离目录创建、rename、核对、删除、恢复及空目录删除的每个失败出口都应明确保留位置。恢复不得采用可能覆盖新路径的普通 rename；不支持安全恢复时保留隔离源并警告。
4. 仅删除已核对对象和自身已空的临时目录；不递归删除，不遍历清理历史草稿。
5. 警告不得进入 TOML、批准源 JSON 或 stdout；两个调用点须在后续可能返回错误之前向 stderr 输出。
6. 同步稳定规格及帮助中的自动消费、外部源保留、清理失败成功退出和可恢复路径规则；目前稳定规格尚未包含这项新行为。

以上均是 Revision 2 已有设计的落实要点，无新增阻塞性修正要求。
